# Учет истории диалога и LLM Query Rewriting

## 1. Цель доработки

В MVP необходимо научить MedTrust обрабатывать уточняющие вопросы регистратора с учетом предыдущего диалога.

Текущая проблема:

```text
Вопрос: Состав анализа ОАК
Ответ: ...
Вопрос: стоимость
Поиск: стоимость
```

Из-за отсутствия контекста RAG получает слишком общий запрос и может вернуть нерелевантные фрагменты.

Ожидаемое поведение:

```text
История: Состав анализа ОАК -> ответ
Текущий вопрос: стоимость
Запрос в RAG: Стоимость анализа ОАК
```

В рамках MVP используется подход **LLM Query Rewriting**:

```text
История диалога + текущий вопрос
        ↓
LLM Contextualizer
        ↓
Самостоятельный поисковый запрос
        ↓
RAG
        ↓
Проверка достаточности источников
        ↓
LLM Answer Generation
```

LLM Contextualizer не отвечает на вопрос регистратора и не является источником фактической информации. Его задача — восстановить смысл текущего запроса, исправить очевидные опечатки и подготовить запрос для поиска.

## 2. Границы MVP

В MVP необходимо реализовать:

- хранение идентификатора диалога;
- передачу недавней истории вопросов и ответов в Contextualizer;
- формирование самостоятельного `resolved_query`;
- определение сущностей и намерения запроса;
- исправление очевидных опечаток с помощью LLM;
- использование словаря медицинских терминов при наличии такого словаря;
- возврат оценки уверенности;
- запрос уточнения при неоднозначности;
- передачу в RAG только нормализованного поискового запроса;
- сохранение исходного и нормализованного вариантов запроса;
- проверку результата на тестовых диалогах.

В MVP не требуется:

- строить автономного агента;
- выполнять несколько последовательных вызовов LLM для одного простого вопроса;
- передавать в LLM всю историю диалога без ограничения;
- изменять исходную базу знаний автоматически;
- использовать LLM Contextualizer как генератор ответа пользователю.

## 3. Изменения в модели запроса

Текущий endpoint обработки запросов должен принимать `conversation_id` и, при необходимости, контекст текущей записи или услуги.

Пример входного запроса:

```json
{
  "conversation_id": "uuid",
  "question": "стоимость",
  "appointment_context": {
    "service": "ОАК"
  }
}
```

`appointment_context` является дополнительным структурированным контекстом. Он не должен без необходимости смешиваться с текстом истории или автоматически превращаться в текстовый embedding-запрос.

Для каждого сообщения необходимо сохранять:

```json
{
  "message_id": "uuid",
  "conversation_id": "uuid",
  "raw_question": "стоимость",
  "resolved_query": "Стоимость анализа ОАК",
  "resolved_entities": {
    "service": "ОАК"
  },
  "intent": "follow_up",
  "confidence": 0.94,
  "depends_on_message_id": "previous-message-id",
  "created_at": "timestamp"
}
```

Исходный вопрос нельзя заменять нормализованным: оба значения нужны для аудита, аналитики и оценки качества переписывания.

## 4. Состояние диалога

Для каждого `conversation_id` необходимо хранить состояние, достаточное для восстановления темы разговора.

Минимальная структура:

```json
{
  "conversation_id": "uuid",
  "active_topic": "ОАК",
  "entities": {
    "service": "ОАК",
    "department": "лаборатория"
  },
  "last_resolved_query": "Состав анализа ОАК",
  "recent_messages": [
    {
      "role": "user",
      "text": "Состав анализа ОАК"
    },
    {
      "role": "assistant",
      "text": "ОАК включает ..."
    }
  ],
  "updated_at": "timestamp"
}
```

Правила хранения контекста:

- передавать в Contextualizer ограниченное число последних сообщений;
- хранить последний нормализованный запрос отдельно от текста ответа;
- хранить выделенные сущности отдельно от свободного текста;
- обновлять `active_topic` после каждого успешно разрешенного запроса;
- начинать новый диалог при явном сбросе пользователем или по правилам интерфейса;
- не считать любой предыдущий ответ актуальным контекстом, если в диалоге уже появилась новая тема.

Для длинных диалогов следует использовать краткое резюме предыдущих сообщений, а не передавать всю историю.

## 5. LLM Contextualizer

### 5.1. Входные данные

Contextualizer получает:

- текущий вопрос регистратора;
- несколько последних вопросов и ответов;
- последний `resolved_query`;
- активную тему;
- извлеченные сущности;
- словарь допустимых медицинских терминов, если он используется;
- структурированный контекст текущей услуги, если он доступен.

Контекст пациента не следует включать в переписывание поискового запроса без явной необходимости. Данные пациента должны обрабатываться отдельно и передаваться только в разрешенном объеме.

### 5.2. Обязательные действия модели

LLM должна:

1. определить, является ли вопрос новым или уточняющим;
2. восстановить пропущенный объект вопроса по истории;
3. сформировать самостоятельный запрос для RAG;
4. выделить сущности: услугу, анализ, врача, подразделение, процедуру и другие допустимые объекты;
5. выделить атрибут запроса: стоимость, состав, подготовка, срок, адрес и т. п.;
6. исправить очевидные опечатки;
7. указать уверенность результата;
8. сообщить, требуется ли уточнение у регистратора.

Модель не должна:

- придумывать отсутствующую услугу или медицинский факт;
- добавлять сведения, которых нет в вопросе или истории;
- отвечать на вопрос вместо формирования поискового запроса;
- интерпретировать результаты анализов;
- формировать медицинские рекомендации;
- скрывать неоднозначность низкой уверенностью.

### 5.3. Формат ответа модели

Ответ должен возвращаться в строго заданной JSON-схеме:

```json
{
  "intent": "follow_up",
  "standalone_query": "Стоимость анализа ОАК",
  "entities": {
    "service": "ОАК"
  },
  "facets": [
    {
      "name": "attribute",
      "value": "price"
    }
  ],
  "corrections": [
    {
      "original": "оакк",
      "corrected": "ОАК",
      "source": "medical_dictionary"
    }
  ],
  "confidence": 0.94,
  "clarification_required": false,
  "clarification_question": null
}
```

Допустимые значения `intent` должны быть ограничены перечислением, например:

- `new_question` — самостоятельный новый вопрос;
- `follow_up` — уточнение предыдущего вопроса;
- `compound_question` — вопрос с несколькими подтемами;
- `ambiguous` — недостаточно данных для надежного разрешения;
- `out_of_scope` — запрос не относится к поддерживаемому сценарию.

Если модель не может надежно восстановить объект, она должна вернуть:

```json
{
  "intent": "ambiguous",
  "standalone_query": null,
  "entities": {},
  "facets": [],
  "corrections": [],
  "confidence": 0.42,
  "clarification_required": true,
  "clarification_question": "Стоимость какого анализа вы имеете в виду?"
}
```

## 6. Исправление опечаток

Для повышения устойчивости поиска следует использовать два источника нормализации.

### 6.1. LLM

LLM может исправлять опечатки в свободном тексте и восстанавливать смысл коротких запросов:

```text
стоимоть оак
→ Стоимость анализа ОАК
```

Исправление разрешено только при достаточной уверенности и должно сохраняться в поле `corrections`.

### 6.2. Словарь медицинских терминов

Словарь рекомендуется использовать как проверяемый источник допустимых сущностей, а не как отдельную базу ответов.

В словаре следует хранить:

```json
{
  "canonical": "ОАК",
  "aliases": [
    "общий анализ крови",
    "клинический анализ крови"
  ],
  "common_typos": [
    "оакк",
    "оак"
  ],
  "entity_type": "laboratory_test"
}
```

Словарь может использоваться для:

- проверки результата LLM;
- выбора канонического названия сущности;
- поиска по синонимам и распространенным опечаткам;
- формирования фильтров для RAG;
- снижения риска того, что модель заменит термин на неподтвержденный.

При конфликте между историей и словарем нельзя автоматически выбирать вариант без проверки уверенности. В сомнительном случае нужно попросить регистратора уточнить термин.

## 7. Передача запроса в RAG

RAG должен получать самостоятельный нормализованный запрос, а не только исходный текст:

```json
{
  "query": "Стоимость анализа ОАК",
  "facets": [
    {
      "name": "service",
      "value": "ОАК"
    },
    {
      "name": "attribute",
      "value": "price"
    }
  ],
  "conversation_id": "uuid",
  "source_message_id": "message-id"
}
```

Для составного вопроса Contextualizer должен выделить несколько подзапросов либо передать фасеты, которые позволят оркестратору выполнить отдельный поиск по каждой теме.

Пример:

```text
Как подготовиться к ОАК и сколько он стоит?
```

```text
1. Подготовка к анализу ОАК
2. Стоимость анализа ОАК
```

В ответ генератору необходимо передавать:

- исходный вопрос;
- `resolved_query`;
- найденные фрагменты;
- источники и их идентификаторы;
- результаты `Answerability Check`.

Генератор ответа не должен использовать `resolved_query` как доказательство факта. Это только поисковая формулировка.

## 8. Обработка низкой уверенности

Нельзя передавать результат в RAG как достоверный, если Contextualizer обнаружил неоднозначность.

Минимальная логика:

```text
confidence >= заданного порога
    → выполнить поиск по resolved_query

confidence < заданного порога
    → задать уточняющий вопрос
```

Порог должен быть настраиваемым и проверяться на тестовом наборе диалогов. Одного числового значения от модели недостаточно: желательно дополнительно проверять:

- наличие объекта запроса;
- соответствие сущности истории;
- наличие допустимого термина в словаре;
- отсутствие противоречий между текущим вопросом и контекстом.

## 9. Проверка достаточности ответа

После RAG необходимо выполнять `Answerability Check`.

Проверка должна определить:

- найден ли объект вопроса;
- найден ли требуемый атрибут;
- покрыты ли все фасеты;
- достаточно ли релевантны источники;
- нет ли противоречий между документами.

Пример:

```json
{
  "answerable": false,
  "covered_facets": ["service"],
  "missing_facets": ["price"],
  "reason": "service_found_but_price_missing"
}
```

Если информации недостаточно:

1. зафиксировать пробел с исходным и нормализованным запросом;
2. не просить генератор придумывать ответ;
3. для разрешенных административных сценариев запустить предусмотренный резервный сценарий;
4. для медицинских вопросов выполнить маршрутизацию к медицинскому работнику.

## 10. Логирование и аналитика

Для каждого запроса необходимо логировать:

- `conversation_id`;
- исходный вопрос;
- контекст, использованный для переписывания;
- `resolved_query`;
- исправления опечаток;
- найденные сущности и фасеты;
- значение уверенности;
- результат поиска;
- ответ регистратора на уточняющий вопрос, если он был;
- пользовательскую оценку ответа;
- факт ручного исправления результата.

В логах нельзя хранить избыточные персональные и медицинские данные. Контекст должен быть минимальным, а доступ к журналам — ролевым.

Нужно отдельно считать:

- долю уточняющих вопросов, разрешенных без участия пользователя;
- долю ошибочных переписываний;
- долю запросов, для которых потребовалось уточнение;
- качество исправления опечаток;
- `Recall@k` и `Precision@k` для поиска после переписывания;
- долю ответов без достаточного источника;
- задержку и стоимость вызова Contextualizer.

## 11. Требования к промпту Contextualizer

Системный промпт должен явно задавать:

- роль модели: преобразование запроса для поиска;
- запрет на генерацию фактического ответа;
- запрет на добавление отсутствующих сущностей;
- приоритет непосредственного текущего вопроса над устаревшим контекстом;
- формат JSON без дополнительного текста;
- допустимые значения `intent`;
- правила обработки неоднозначности;
- правила работы со словарем медицинских терминов;
- необходимость сохранять исходную формулировку.

Рекомендуется версионировать промпт и сохранять его версию в диагностике запроса.

## 12. Тестовые сценарии приемки

До включения функции необходимо подготовить набор размеченных диалогов.

Минимальный набор:

| Сценарий | Ожидаемый результат |
| --- | --- |
| «Состав ОАК» → «стоимость» | «Стоимость анализа ОАК» |
| «ОАК» → «подготовка» | «Подготовка к анализу ОАК» |
| «УЗИ ОБП» → «а если беременность?» | Запрос уточнения или корректное использование разрешенного контекста |
| «стоимоть оак» | Исправление опечатки и поиск по ОАК |
| «анализ крови» → «срок» | Запрос уточнения, если вид анализа не определен |
| ОАК → новый вопрос про травмпункт | Переключение активной темы |
| Две темы в последних сообщениях → «стоимость» | Запрос уточнения |
| Медицинская рекомендация | Не генерировать рекомендацию, выполнить маршрутизацию |
| Сущность отсутствует в словаре | Не подменять термин догадкой |

Для каждого сценария необходимо проверять не только текст ответа, но и:

- какой запрос ушел в RAG;
- какие сущности были выделены;
- была ли корректно определена тема;
- не появились ли неподтвержденные сведения;
- сохранились ли исходный и нормализованный запросы.

## 13. Порядок реализации

### Этап 1. Состояние диалога

- добавить `conversation_id`;
- определить срок жизни диалога;
- сохранять сообщения и последний `resolved_query`;
- реализовать сброс и переключение темы.

### Этап 2. Контракт Contextualizer

- зафиксировать JSON-схему;
- реализовать вызов LLM;
- добавить валидацию ответа по схеме;
- реализовать повторный вызов или безопасное завершение при некорректном JSON.

### Этап 3. Нормализация терминов

- подготовить начальный словарь медицинских терминов;
- добавить канонические названия, синонимы и частые опечатки;
- проверять результаты LLM по словарю;
- сохранять исправления.

### Этап 4. Интеграция с RAG

- передавать `resolved_query` вместо необработанного короткого вопроса;
- добавить фасеты;
- сохранить исходный вопрос для ответа и аналитики;
- добавить диагностику поиска.

### Этап 5. Проверка качества

- собрать размеченный набор диалогов;
- сравнить поиск до и после Query Rewriting;
- измерить качество контекста, поиск и задержку;
- проверить сценарии с неоднозначностью и переключением темы;
- провести проверку безопасности и ограничения передачи данных.

## 14. Критерии готовности MVP

MVP считается готовым, если:

- уточняющий вопрос учитывает предыдущую тему;
- короткие вопросы вроде «стоимость» корректно превращаются в самостоятельный запрос;
- распространенные опечатки исправляются без изменения смысла;
- неоднозначные запросы приводят к уточнению, а не к случайному поиску;
- в RAG передается `resolved_query` и необходимые фасеты;
- исходный вопрос и результат переписывания доступны в диагностике;
- ответ формируется только на основании найденных источников;
- запросы о медицинской рекомендации не превращаются в свободный ответ;
- качество переписывания измеряется на заранее подготовленном наборе тестов;
- добавленная задержка и стоимость вызова LLM приемлемы для целевого времени ответа.
