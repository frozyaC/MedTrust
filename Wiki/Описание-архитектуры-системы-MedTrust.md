# MedTrust — логическая архитектура системы



## 1. Назначение



**MedTrust** — интеллектуальный справочник регистратора медицинской клиники, работающий поверх существующей базы знаний клиники.



Система предназначена для того, чтобы:



1. быстро находить релевантную информацию в базе знаний;

2. формировать из найденной информации структурированный ответ для регистратора;

3. учитывать доступный контекст пациента;

4. явно выявлять ситуации, когда в базе знаний недостаточно информации;

5. фиксировать пробелы в знаниях и предоставлять аналитику владельцу базы знаний;

6. контролировать потенциальные противоречия между документами;

7. собирать обратную связь по качеству ответов и использовать ее для улучшения системы.



MedTrust **не является медицинской информационной системой и не заменяет АРМ/CRM клиники**. Система использует существующие корпоративные данные как внешние источники и не должна изменять их напрямую.



---



# 2. Архитектурная модель



На логическом уровне MedTrust состоит из трех основных контуров:



### 2.1. Контур обработки запросов



Отвечает за обработку запроса регистратора и формирование ответа.



Основные компоненты:



* Query Orchestration;

* Retrieval / RAG;

* Confidence / Answerability Check;

* Answer Generation;

* Safety / Guardrails.



### 2.2. Контур обработки и контроля знаний



Отвечает за подготовку знаний для поиска и контроль качества самой базы знаний.



Основные компоненты:



* Knowledge Ingestion;

* внутренняя поисковая индексация;

* Карта пробелов;

* Проверка непротиворечивости и актуальности.



### 2.3. Контур Feedback / Quality Loop



Отвечает за получение информации о качестве работы системы и передачу результатов:



* владельцу базы знаний;

* разработчикам / ИТ.



Feedback Loop является **сквозным механизмом**, а не изолированным этапом обработки запроса.

# 3. Внешние системы и участники



MedTrust взаимодействует с пятью основными внешними сущностями.



| Система / роль                 | Направление | Назначение                                            |

| ------------------------------ | ----------- | ----------------------------------------------------- |

| Регистратор                    | ↔ MedTrust  | Ввод запроса, получение ответа, обратная связь        |

| АРМ / CRM клиники              | → MedTrust  | Передача контекста пациента                           |

| База знаний клиники            | → MedTrust  | Передача корпоративных знаний                         |

| GigaChat                       | ↔ MedTrust  | Генерация и обработка ответа                          |

| Web Search / внешние источники | ↔ MedTrust  | Резервный поиск при отсутствии достаточной информации |



Отдельными пользователями аналитического и административного контура являются:



* заведующий регистратурой / владелец базы знаний;

* ИТ / разработчики.

# 4. Источники истины и границы ответственности



В системе должны быть четко разделены источники данных.



## 4.1. База знаний клиники



**Основной источник истины для корпоративных знаний клиники.**



Именно из нее должны формироваться ответы на вопросы, связанные с:



* внутренними правилами;

* процедурами клиники;

* организацией приема;

* подготовкой к процедурам;

* внутренними инструкциями;

* другой информацией, которую клиника считает нормативной для своих сотрудников.



MedTrust получает данные из базы знаний, но **не изменяет исходную базу напрямую**.



## 4.2. АРМ / CRM



**Источник актуального контекста пациента.**



АРМ / CRM передает в MedTrust доступные данные пациента, например:



* возраст;

* пол;

* беременность и срок беременности, если поле включено для конкретного сценария;

* хронические заболевания, если гипотеза о практической пользе этого поля подтверждена.

В MVP пациентский контекст передается в одном JSON с фиксированной схемой и только этими полями: пол и возраст являются обязательными; беременность и срок беременности — опциональными; хронические заболевания пока остаются проверяемым опциональным полем. Сведения о текущей записи и услуге могут передаваться как отдельный контекст запроса. Один и тот же JSON используется для GigaChat и Web Search.



MedTrust не должен изменять данные пациента в АРМ / CRM.



## 4.3. Интернет / внешние источники



Является **дополнительным, а не основным источником информации**.



Используется только в случае, если корпоративная база знаний не содержит достаточной информации для ответа.



Информация из внешних источников должна быть явно маркирована как внешняя и не должна автоматически рассматриваться как подтвержденное знание клиники.



## 4.4. GigaChat



GigaChat является **моделью генерации и обработки текста**, а не самостоятельным источником истины.



LLM должна формировать ответ на основе переданного ей контекста.



Фактическая информация, используемая в ответе, должна поступать из найденных источников, а не «возникать» только на основании генерации модели.

# 5. Контур обработки запроса



## 5.1. Query Orchestration



Query Orchestration — центральный компонент обработки запроса.



Он отвечает за:



* прием запроса регистратора;

* получение и подготовку контекста пациента;

* запуск поиска;

* передачу найденного контекста на оценку достаточности;

* выбор дальнейшего сценария;

* передачу данных на генерацию ответа;

* возврат результата регистратору.



Упрощенная логика:



```text

Запрос регистратора

        ↓

Query Orchestration

        ↓

Retrieval / RAG

        ↓

Confidence / Answerability Check

      ↙              ↘

  достаточно        недостаточно

      ↓                  ↓

GigaChat           Web Search

      ↘                  ↙

       Answer Generation

              ↓

       Safety / Guardrails

              ↓

       Ответ регистратору

```



---



# 6. Retrieval / RAG



## 6.1. Назначение



Компонент выполняет семантический поиск по внутреннему представлению базы знаний.



В процессе подготовки знаний используются:



* разбиение документов на фрагменты;

* embeddings;

* векторизация;

* построение поискового индекса.



При запросе пользователя Retrieval:



1. принимает вопрос;

2. преобразует его в поисковое представление;

3. выполняет поиск релевантных фрагментов;

4. возвращает найденный контекст;

5. при наличии соответствующей информации передает его дальше.



Конкретная модель embeddings и конкретное векторное хранилище на уровне логической архитектуры **не фиксируются**.



---



# 7. Confidence / Answerability Check



Этот компонент является обязательным промежуточным этапом.



Его задача — определить не просто, **найден ли какой-либо документ**, а достаточно ли найденной информации для формирования надежного ответа.



Возможны два результата:



### Достаточно данных



Контекст передается в Answer Generation.



### Недостаточно данных



Запускается дополнительный сценарий:



* регистрация пробела в знаниях;

* при необходимости — поиск во внешних источниках.



Таким образом, решение о переходе в Интернет принимается не просто по факту «поиск ничего не вернул», а по результату проверки достаточности найденного контекста.

В MVP при недостатке данных сначала фиксируется пробел в базе знаний, затем запускается Web Search. Найденная информация явно маркируется как внешняя и требует проверки. После тестирования Web Search может быть ограничен утвержденными ресурсами или отключен.



---



# 8. Answer Generation



Answer Generation использует GigaChat для преобразования найденного контекста в структурированный ответ.



На вход может поступать:



* исходный вопрос;

* релевантные фрагменты базы знаний;

* контекст пациента;

* результаты внешнего поиска;

* дополнительные системные ограничения.



На выходе:



* структурированный текст ответа;

* ссылки / указание источников;

* при необходимости — предупреждение;

* информация о происхождении данных.

Контекст пациента передается в GigaChat и Web Search в одном и том же JSON-формате с фиксированными полями. Это не означает, что контекст автоматически обезличен: до запуска клиника должна проверить состав данных, правовое основание, доступы и условия обработки у поставщиков.



Принцип:



> GigaChat формулирует ответ на основании предоставленного контекста; отсутствие достаточного контекста не должно компенсироваться свободным домыслом модели.

# 9. Web Search / внешние источники



Web Search является резервным механизмом.



Сценарий использования:



```text

Вопрос

  ↓

Поиск в БЗ

  ↓

Недостаточно информации

  ↓

Web Search

  ↓

Полученные материалы

  ↓

GigaChat

  ↓

Структурированный ответ

```



Ответ, сформированный с использованием внешнего поиска, должен иметь явную маркировку, например:



**Источник: Интернет**



и предупреждение:



**Информация получена из внешнего источника и требует дополнительной проверки.**



При этом внешняя информация **не должна автоматически записываться в корпоративную базу знаний**.



Решение о ее добавлении в БЗ принимает ответственный сотрудник вне MedTrust или через предусмотренный отдельный административный процесс.

# 10. Safety / Guardrails



Safety / Guardrails — завершающий контрольный контур перед выдачей ответа пользователю.



Его назначение:



* снижать риск выдуманных ответов;

* проверять наличие достаточного основания для ответа;

* контролировать использование внешних источников;

* отделять справочную информацию от медицинских рекомендаций;

* отображать предупреждения в рискованных или неоднозначных сценариях.



Особенно важно не допускать превращения MedTrust в систему самостоятельной диагностики или назначения лечения.



В рамках проекта следует определить отдельные правила:



* какие вопросы система вообще имеет право обрабатывать;

* когда требуется отказ от ответа;

* когда необходима передача вопроса медицинскому специалисту;

* какие типы информации запрещено формировать автоматически.



Эти правила являются **архитектурным требованием**, но их конкретная формализация — TBD.

# 11. Knowledge Ingestion



Knowledge Ingestion отвечает за загрузку и подготовку материалов из существующей базы знаний клиники.



Логическая цепочка:



```text

База знаний клиники

        ↓

Connector / синхронизация

        ↓

Загрузка документа

        ↓

Парсинг / нормализация

        ↓

Разбиение на фрагменты

        ↓

Embeddings

        ↓

Поисковый индекс

        ↓

Retrieval

```



Источник может быть представлен:



* Wiki.js;

* Markdown-файлами;

* Confluence;

* Notion;

* внутренней БД;

* другим структурированным источником.



На логическом уровне конкретный способ подключения каждого источника не фиксируется.



MedTrust поддерживает **производное поисковое представление знаний**, но это не означает, что оно становится самостоятельной заменой исходной БЗ.

# 12. Контроль непротиворечивости и актуальности



Компонент запускается при:



* добавлении нового документа;

* изменении существующего документа;

* обновлении версии документа.



Упрощенный процесс:



```text

Новый / измененный документ

            ↓

Проверка существующих знаний

            ↓

Сопоставление утверждений

            ↓

Обнаружен потенциальный конфликт?

          ↙       ↘

        Нет        Да

        ↓           ↓

     Индексация    Alert

                    ↓

             Владелец БЗ

```



Система должна выявлять **потенциальные противоречия**, а не автоматически определять абсолютную истинность документов.



Например:



```text

Документ A:

«Подготовка начинается за 8 часов»



Документ B:

«Подготовка начинается за 12 часов»



→ Потенциальная коллизия

→ Требуется проверка владельца БЗ

```



Для повышения качества в дальнейшем рекомендуется учитывать:



* дату документа;

* номер версии;

* статус документа;

* тип источника;

* приоритет / авторитетность источника.

# 13. Карта пробелов



Карта пробелов представляет собой аналитический контур, который собирает случаи, когда существующая база знаний не позволила сформировать достаточный ответ.



Пример:



```text

Запрос регистратора

        ↓

Retrieval

        ↓

Недостаточно данных

        ↓

Knowledge Gap Event

        ↓

Карта пробелов

```



Для каждого события желательно сохранять:



* текст запроса или его обезличенное представление;

* дату и время;

* категорию запроса;

* найденный / ненайденный контекст;

* результат проверки достаточности;

* факт обращения к внешнему поиску;

* итоговую обратную связь, если она была.



Необходимо учитывать требования к защите персональных данных: содержание события не должно содержать больше данных пациента, чем действительно требуется для аналитики.



Карта пробелов предоставляет:



* количество пробелов;

* динамику по времени;

* наиболее частые темы;

* темы с высокой частотой обращений;

* потенциальные приоритеты для расширения БЗ.

# 14. Feedback / Quality Loop



После выдачи ответа регистратор может оставить:



* 👍 — ответ полезен;

* 👎 — ответ бесполезен / нерелевантен;

* текстовый комментарий.



Feedback связывается с конкретным ответом и исходным запросом.



Логический поток:



```text

Ответ

  ↓

Регистратор

  ↓

👍 / 👎 / комментарий

  ↓

Feedback / Quality Loop

      ↙             ↘

Владелец БЗ      ИТ / разработчики

```



## Для владельца БЗ



Feedback помогает выявлять:



* недостающие статьи;

* неясные формулировки;

* устаревшие сведения;

* ошибочные или конфликтующие документы.



## Для разработчиков



Feedback используется для анализа:



* качества Retrieval;

* релевантности найденных фрагментов;

* качества формирования ответа;

* случаев ложного отказа;

* случаев нерелевантной выдачи;

* ошибок маршрутизации запроса.



Feedback **не должен автоматически изменять алгоритмы системы или базу знаний**.



Он является источником данных для последующего управляемого улучшения.

# 15. Работа с контекстом пациента



При наличии интеграции с АРМ / CRM MedTrust может использовать контекст пациента для персонализации ответа.



Логически:



```text

АРМ / CRM

    ↓

API

    ↓

MedTrust

    ↓

Query Orchestration

    ↓

Retrieval + Context

    ↓

Answer Generation

```



Контекст пациента не должен без необходимости попадать:



* в логи;

* в аналитику;

* в Feedback;

* в сообщения разработчикам.



Необходимо разделять:



**данные, необходимые для текущего ответа**



и



**данные, необходимые для хранения / аналитики**.



На уровне MVP точный набор передаваемых полей должен быть утвержден отдельно.

**АРМ / CRM → MedTrust**

Направление:



**MedTrust ↔ GigaChat**

* передача запроса;

Логическое взаимодействие:



**MedTrust → Web Search → MedTrust**



Назначение:



получение внешних материалов при недостатке информации в БЗ.

# 18. Внутренние хранилища MedTrust



Логическая архитектура предполагает наличие внутренних производных данных.



Как минимум потребуются сущности:



### Search Index



Хранит поисковое представление документов:



* chunks;

* embeddings;

* метаданные;

* идентификатор исходного документа;

* версию документа.



### Query / Answer Log



Хранит информацию о взаимодействиях системы:



* запрос;

* результаты поиска;

* служебные метрики;

* сформированный ответ;

* идентификаторы источников;

* информацию о feedback.



### Gap Store



Хранит обнаруженные пробелы и их статистику.



### Feedback Store



Хранит обратную связь пользователей.



### Conflict / Alert Store



Хранит обнаруженные потенциальные конфликты и их состояние.



Конкретная СУБД / vector database / структура таблиц на уровне логической архитектуры **не фиксируется**.

# 19. Жизненный цикл знаний



Логический жизненный цикл документа:



```text

Источник клиники

      ↓

Получение

      ↓

Нормализация

      ↓

Проверка непротиворечивости

      ↓

Индексация

      ↓

Использование в Retrieval

      ↓

Получение Feedback

      ↓

Выявление проблем

      ↓

Обновление документа

      ↓

Повторная проверка

```



Таким образом, Feedback Loop влияет не только на качество ответов, но и на качество самого набора знаний.

# 20. Что система не делает



Чтобы архитектурные границы не размывались, MedTrust в текущей концепции:



* не изменяет данные пациента в АРМ / CRM;

* не заменяет основную базу знаний клиники;

* не является системой диагностики;

* не принимает клинические решения самостоятельно;

* не записывает найденную в Интернете информацию автоматически в БЗ;

* не считает внешний источник автоматически достоверным;

* не определяет самостоятельно окончательно, какой из конфликтующих документов является правильным;

* не изменяет алгоритмы поиска автоматически только на основании одного feedback-события.

# 21. Основные архитектурные принципы



1. **Corporate Knowledge First**

   Корпоративная база знаний является главным источником информации.



2. **Evidence Before Generation**

   Генерация ответа производится на основании найденного контекста.



3. **Answerability Before Web**

   Внешний поиск используется после проверки недостаточности корпоративного контекста.



4. **External Source Transparency**

   Внешняя информация всегда явно маркируется.



5. **Read-only Integrations**

   АРМ / CRM и исходная база знаний используются в режиме чтения.



6. **Human Validation**

   Решение по изменению корпоративной базы знаний и разрешению конфликтов остается за ответственным сотрудником.



7. **Continuous Improvement**

   Пробелы и feedback образуют контур постоянного улучшения.



8. **Separation of Concerns**

   Поиск, генерация ответа, обработка знаний, аналитика и контроль качества должны быть логически разделены.

# 23. Что пока не следует считать зафиксированным



Следующие решения требуют отдельного технического проектирования:



* конкретный vector database;

* конкретная модель embeddings;

* конкретный механизм Web Search;

* способ аутентификации API;

* формат API АРМ / CRM;

* формат подключения Wiki.js / Confluence / Notion;

* модель хранения персональных данных;

* конкретные правила Safety / Guardrails;

* модель оценки confidence;

* способ разрешения конфликтов документов;

* политика хранения и обезличивания логов;

* RBAC и детальная ролевая модель;

* схема отказоустойчивости и мониторинга.



Эти вопросы не должны «зашиваться» в логическую архитектуру до принятия соответствующих технических решений.
