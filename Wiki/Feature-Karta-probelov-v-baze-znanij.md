# Фича: карта пробелов в базе знаний

## 1. Краткое описание

Фича превращает обращения регистраторов в управляемый контур улучшения базы знаний:

1. регистратор задает вопрос;
2. MedTrust исправляет очевидные опечатки и восстанавливает смысл уточняющего вопроса по контексту переписки;
3. поиск сначала выполняется по корпоративной базе знаний (БЗ);
4. если БЗ не содержит достаточного основания для ответа, система автоматически фиксирует пробел;
5. если ответ выдан, регистратор может оценить его и указать причину отрицательной оценки;
6. причина «в БЗ нет ответа» создает пробел, а остальные причины создают запись о проблеме качества системы для разработчиков/ИТ.

Записи сохраняются в PostgreSQL как отдельные события. Поверх событий добавляется автоматическая группировка семантически схожих пробелов: исходные вопросы не теряются, а владелец БЗ получает приоритетные группы и может закрыть группу целиком или отдельные вопросы. Категоризация пробелов, назначение исполнителей и автоматическое изменение Wiki.js не входят в эту фичу.

Фича не меняет исходную БЗ и не записывает в нее сведения, найденные через Web Search. Решение о добавлении или исправлении статьи принимает владелец БЗ.

## 2. Ценность для клиента

### Для заведующего регистратурой и владельца БЗ

- становится виден фактический список вопросов, на которые сотрудники не получают ответа;
- можно приоритизировать написание инструкций по частоте обращений и влиянию на работу;
- сокращается зависимость от устных подсказок опытных сотрудников;
- появляется измеримый путь от вопроса до статьи: «пробел обнаружен → проверен → закрыт».

### Для директора клиники

- уменьшается время ожидания пациента и нагрузка на старших администраторов;
- качество БЗ контролируется по реальным рабочим сценариям, а не только по плановой проверке документов;
- можно оценивать эффект внедрения по доле запросов без достаточного ответа и времени закрытия пробела.

### Для регистратора

- не нужно отдельно запоминать или передавать руководителю нерешенный вопрос;
- отрицательная оценка ответа занимает один шаг и не требует писать длинный комментарий;
- улучшение и наполнение базы знаний в соответствии с потребностями регистратора.

Целевые продуктовые ориентиры из Lean Canvas: сократить время поиска примерно с 2 минут до 30 секунд и снизить долю запросов без ответа с 30–40% до менее 15%. Для этой фичи дополнительно измеряются количество выявленных пробелов и время от фиксации до закрытия.

## 3. Термины

| Термин | Определение |
| --- | --- |
| Исходный вопрос (`raw_question`) | Текст, введенный регистратором. Не заменяется нормализованным вариантом. |
| Нормализованный запрос (`resolved_query`) | Самостоятельная поисковая формулировка после учета истории, исправления опечаток и выделения сущностей. |
| Достаточность БЗ | Наличие релевантного и предметного фрагмента корпоративной БЗ, который дает основание ответить на вопрос. Наличие любого похожего документа недостаточно. |
| Автоматический пробел | Событие, созданное по результату `Answerability Check`, если корпоративная БЗ недостаточна. |
| Подтвержденный пробел | Событие, созданное после отрицательной оценки ответа с причиной `no_knowledge_base_answer`. |
| Проблема качества системы | Событие отрицательной обратной связи, которое не означает отсутствие знания в БЗ: ошибка поиска, переписывания, генерации, формата или интерфейса. |
| Закрытие пробела | Подтверждение ответственным сотрудником, что БЗ дополнена/исправлена и вопрос снова имеет достаточное покрытие. |

## 4. Бизнес-правила

### 4.1. Порядок обработки запроса

1. Сохраняется `conversation_id`; в Contextualizer передаются только ограниченные последние сообщения, резюме и последний `resolved_query`.
2. Сохраняются `raw_question`, `resolved_query`, уверенность переписывания, сущности и связь с предыдущим сообщением.
3. Выполняется поиск по корпоративной БЗ.
4. `Answerability Check` оценивает не только наличие результатов, но и предметность источников, покрытие вопроса и потенциальные противоречия.
5. Если БЗ недостаточна, пробел создается **до** резервного Web Search. Даже если внешний поиск помог сформировать ответ, исходный пробел БЗ не исчезает.
6. Ответ на основе Web Search явно помечается как внешний и требует проверки. Внешний текст не становится статьей автоматически.
7. После ответа показываются источники и действия обратной связи.

### 4.2. Когда создается автоматический пробел

Создавать пробел, если выполняется хотя бы одно условие:

- релевантных фрагментов БЗ нет;
- найденные фрагменты относятся к теме, но не отвечают на сформулированный вопрос;
- покрыта только часть составного вопроса;
- найденные документы противоречат друг другу и надежный ответ без решения владельца БЗ невозможен;
- ответ был явно заменен безопасным сообщением о недостатке данных.

Не создавать автоматический пробел только из-за:

- низкой уверенности Contextualizer, если система сначала запросила уточнение;
- технической ошибки БД, LLM, embeddings или Web Search;
- временной недоступности интерфейса;
- отрицательной оценки ответа, если причина относится к формату, релевантности или техническому качеству.

Если вопрос неоднозначен и система задала уточнение, пробел фиксируется только после выполнения уточненного запроса и проверки БЗ. Это предотвращает запись шумных пробелов из коротких фраз вроде «стоимость».

### 4.3. Когда создается пробел по feedback

Отрицательная оценка открывает выбор причины. При выборе `no_knowledge_base_answer` создается пользовательский пробел, связанный с конкретным `query_id`.

Если уже есть автоматический пробел по тому же запросу, новая запись все равно сохраняется как отдельное feedback-событие. В MVP записи не объединяются и не скрываются; аналитика может позднее связать их по `query_id` или `normalized_query_hash`.

Один ответ можно оценить один раз для одного регистратора/клиента. Повторная отправка должна быть идемпотентной по идентификатору ответа и пользователю, если в системе доступна аутентификация.

### 4.4. Что не считается доказательством пробела

- Регистратор не прочитал источник или не раскрыл цитату.
- Ответ показан с Web Search, если одновременно есть достаточный источник в БЗ: внешний источник в этом случае не доказывает пробел.
- Ответ не понравился из-за длины или оформления.
- Регистратор задал новый вопрос в том же диалоге, но тема была корректно переключена.

## 5. Причины отрицательной оценки

Причины должны быть короткими кнопками, а в БД храниться стабильными кодами. Рекомендуемый набор для пилота:

| Код | Текст кнопки | Куда направляется | Создает пробел БЗ |
| --- | --- | --- | --- |
| `no_knowledge_base_answer` | Нет ответа в базе знаний | Владелец БЗ | Да |
| `knowledge_incomplete` | Ответ неполный | Владелец БЗ; может потребоваться проверка системы | Да, если регистратор подтверждает отсутствие части инструкции |
| `knowledge_outdated` | Информация устарела | Владелец БЗ | Да, как задача на обновление |
| `answer_irrelevant` | Ответ не по моему вопросу | Разработчики: Retrieval/Contextualizer; при подтверждении отсутствия статьи — владелец БЗ | Нет автоматически |
| `answer_incorrect` | Ответ противоречит правилам или источнику | Разработчики + владелец БЗ | Нет автоматически; возможен отдельный конфликт БЗ |
| `answer_formatting` | Плохое форматирование или трудно читать | Разработчики: Generation/UI | Нет |
| `wrong_context` | Не учтен контекст предыдущего вопроса | Разработчики: ConversationMemory/Contextualizer | Нет |
| `wrong_source` | Показан неподходящий источник | Разработчики: Retrieval/attribution | Нет |
| `technical_error` | Ошибка или ответ не загрузился | Разработчики/ИТ | Нет |
| `other` | Другая причина | Маршрутизация по комментарию | Нет |

Для MVP достаточно включить первые 6–7 причин и `other`. `knowledge_incomplete` и `knowledge_outdated` являются разновидностями работы с БЗ, но не требуют отдельного механизма объединения записей.

Комментарии необязательны для `no_knowledge_base_answer`, но рекомендуются для `other`, `answer_incorrect` и `answer_irrelevant`. Свободный текст не должен заменять код причины.

Если вопрос требует решения врача или информация не обозначена в БЗ явно, специальная кнопка и отдельная маршрутизация не нужны. Регистратор самостоятельно уточняет информацию у врача. MedTrust может только сформировать безопасную рекомендацию уточнить информацию у врача в ответе, если найденных материалов недостаточно для надежного ответа.

## 6. Пользовательские сценарии

### Сценарий A: ответ найден в БЗ

```text
Вопрос → Query Rewriting с историей → поиск по БЗ
       → Answerability = true → ответ + источники → пользователь продолжает работу
```

Регистратор видит `Полезно` и `Плохо`. При выборе `Плохо` сначала выбирает причину, затем при необходимости добавляет комментарий.

### Сценарий B: ответа в БЗ нет

```text
Вопрос → Query Rewriting → поиск по БЗ
       → Answerability = false
       → INSERT automatic gap
       → разрешенный Web Search или безопасное сообщение
       → ответ с маркировкой внешнего источника
```

Регистратор не должен вручную подтверждать автоматический пробел: факт отсутствия покрытия уже определен системой. В интерфейсе можно показать нейтральное сообщение «Вопрос зафиксирован для улучшения базы знаний».

### Сценарий C: найден ответ, но он оценен отрицательно

```text
Ответ → Плохо → причина
                     ├─ no_knowledge_base_answer → INSERT user-confirmed gap
                     └─ другая причина → INSERT quality issue
```

### Сценарий D: вопрос требует уточнения

```text
«Стоимость» → Contextualizer: confidence ниже порога
           → уточняющий вопрос
           → после ответа пользователя выполняется новый query_id
```

Пробел не создается на шаге уточнения, если предметный запрос еще не сформирован.

## 7. Минимальная модель данных первой итерации

Существующие `chat_messages` и `conversation_query_context` являются источниками контекста. В `chat_messages` уже хранится связь сообщения с `query_id` и список источников; это позволяет не дублировать полный ответ в записи пробела.

### 7.1. Таблица `knowledge_gaps`

```sql
CREATE TABLE knowledge_gaps (
    id UUID PRIMARY KEY,
    query_id UUID NOT NULL,
    conversation_id UUID,
    source TEXT NOT NULL CHECK (source IN ('automatic', 'user_feedback')),
    status TEXT NOT NULL DEFAULT 'open'
        CHECK (status IN ('open', 'in_review', 'resolved', 'dismissed')),
    raw_question TEXT NOT NULL,
    resolved_query TEXT,
    reason_code TEXT NOT NULL,
    answerability_reason TEXT,
    source_ids JSONB NOT NULL DEFAULT '[]'::jsonb,
    comment TEXT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    resolved_at TIMESTAMPTZ,
    resolved_by TEXT
);

CREATE INDEX knowledge_gaps_status_created_idx
    ON knowledge_gaps (status, created_at DESC);
CREATE INDEX knowledge_gaps_query_idx
    ON knowledge_gaps (query_id);
```

`reason_code` для автоматической записи обычно равен `no_knowledge_base_answer`, `knowledge_incomplete` или `knowledge_conflict`. Для первой итерации не нужно хранить категорию, кластер, ссылку на будущую статью или назначенного исполнителя.

### 7.2. Таблица `query_feedback`

Текущий endpoint уже принимает оценку, но схема БД должна существовать явно:

```sql
CREATE TABLE query_feedback (
    id UUID PRIMARY KEY,
    query_id UUID NOT NULL,
    rating TEXT NOT NULL CHECK (rating IN ('positive', 'negative')),
    reason_code TEXT,
    comment TEXT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX query_feedback_query_idx
    ON query_feedback (query_id, created_at DESC);
```

`reason_code` обязателен для отрицательной оценки после перехода на новый UI. Положительная оценка причины не имеет.

### 7.3. Таблица `quality_issues`

Можно реализовать отдельной таблицей сразу либо временно хранить такие события в `query_feedback`. Предпочтительный вариант:

```sql
CREATE TABLE quality_issues (
    id UUID PRIMARY KEY,
    feedback_id UUID NOT NULL REFERENCES query_feedback(id) ON DELETE CASCADE,
    query_id UUID NOT NULL,
    issue_code TEXT NOT NULL,
    status TEXT NOT NULL DEFAULT 'open'
        CHECK (status IN ('open', 'in_review', 'resolved', 'dismissed')),
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

Если отдельная таблица откладывается, `query_feedback` должна иметь `kind`/`routing` или эквивалентный признак, чтобы записи для владельца БЗ не смешивались с задачами разработчиков.

## 8. API-контракт

### 8.1. Ответ `POST /api/v1/query`

Нужно сохранить совместимость с текущим `query_id` и добавить диагностический блок:

```json
{
  "query_id": "uuid",
  "conversation_id": "uuid",
  "answer": "Текст ответа",
  "sources": [],
  "query": {
    "raw_question": "стоимость",
    "resolved_query": "Стоимость анализа ОАК",
    "confidence": 0.94,
    "source_message_id": "uuid"
  },
  "answerability": {
    "corporate_kb_sufficient": false,
    "reason": "relevant_answer_not_found"
  },
  "gap": {
    "created": true,
    "id": "uuid",
    "source": "automatic"
  }
}
```

Не следует возвращать регистратору внутренние оценки, которые могут быть восприняты как медицинская уверенность. Диагностические поля нужны прежде всего для UI, аудита и аналитики и должны учитывать ролевой доступ.

### 8.2. `POST /api/v1/feedback`

Рекомендуемый контракт:

```json
{
  "query_id": "uuid",
  "rating": "negative",
  "reason_code": "no_knowledge_base_answer",
  "comment": "Нет инструкции по подготовке к услуге"
}
```

Сервис должен:

1. проверить существование `query_id` и связанного ответа;
2. сохранить feedback;
3. по `reason_code` создать `knowledge_gaps` или `quality_issues`;
4. вернуть идентификаторы созданных записей;
5. обеспечить идемпотентность повторной отправки.

Пример ответа:

```json
{
  "status": "saved",
  "feedback_id": "uuid",
  "created_gap_id": "uuid",
  "created_issue_id": null
}
```

Коды, отправляемые frontend, должны быть отделены от отображаемого текста. Нельзя смешивать текущие UI-значения `useful/useless` с backend-значениями `positive/negative` без явного маппинга.

## 9. Техническая интеграция

### Backend

1. Добавить миграцию/изменение `SCHEMA_SQL` для `query_feedback`, `knowledge_gaps` и, при необходимости, `quality_issues`.
2. Вынести сохранение feedback и создание производных событий в отдельный сервис или репозиторный метод, чтобы правило маршрутизации не находилось в HTTP-обработчике.
3. В `RagService` после `Answerability Check` зафиксировать пробел до вызова Web Search.
4. Передавать в gap-store `query_id`, `conversation_id`, `raw_question`, `resolved_query`, `answerability_reason`, идентификаторы источников и минимальный контекст.
5. Добавить версию промпта Contextualizer и диагностические поля, если они уже предусмотрены его контрактом.
6. Не записывать в gap-store ФИО, номер карты и лишние медицинские данные. Доступ к пробелам должен быть ролевым.
7. Добавить административное чтение списка пробелов с фильтрами `status`, `source`, `reason_code`, периодом и сортировкой по частоте/дате. В самой первой итерации допускается SQL/внутренний отчет без полноценного UI.

### Frontend

1. После ответа показывать `Полезно`/`Плохо`.
2. При `Плохо` открывать выбор причин из раздела 5; не создавать пробел на самом клике без выбранной причины.
3. Отправлять feedback с `query_id`, а не с локальным ID элемента ленты.
4. Показывать подтверждение сохранения отдельно для пробела и технической проблемы.
5. Для автоматического пробела показывать понятное уведомление без раскрытия внутренних порогов.
6. Сохранять выбранную оценку при обновлении истории диалога, если API возвращает feedback.

### Наблюдаемость и эксплуатация

Логировать без лишних персональных данных:

- `query_id`, `conversation_id`;
- `raw_question` и `resolved_query`;
- результат `Answerability Check`;
- источник создания записи (`automatic`/`user_feedback`);
- код причины и время сохранения;
- идентификаторы источников и факт Web Search.

Ошибку сохранения feedback или пробела нельзя маскировать сообщением об успехе. Ответ API должен содержать явную ошибку, а frontend — предложить повторить отправку.

## 10. Жизненный цикл записи пробела

```text
open → in_review → resolved
  └──────────────→ dismissed
```

- `open`: запись создана, решения владельца БЗ еще нет;
- `in_review`: ответственный проверяет вопрос и существующие документы;
- `resolved`: статья добавлена/изменена или подтверждено, что покрытие достаточно;
- `dismissed`: запись не является пробелом, дубликат или вопрос вне зоны ответственности.

Закрытие записи не должно удалять исходный вопрос, feedback или диагностические данные. Если после закрытия вопрос снова не покрывается, создается новое событие с новой попыткой.

## 11. Метрики и ценность

Минимальный отчет за период:

- количество запросов;
- доля запросов с `corporate_kb_sufficient = false`;
- количество автоматических и пользовательских пробелов;
- распределение по `reason_code`;
- доля отрицательных оценок и доля причин `no_knowledge_base_answer`;
- среднее время от `open` до `resolved`;
- количество повторных обращений по тому же `query_id`/нормализованному запросу;
- доля ответов из БЗ по сравнению с ответами с Web Search;
- доля технических проблем среди отрицательных оценок.

На пилоте не следует использовать число сырых записей как единственную KPI: без объединения похожих вопросов оно завышает количество проблем. До появления кластеризации основными показателями являются доля запросов без достаточного покрытия, медианное время закрытия и распределение частотных нормализованных запросов.

## 12. Группировка схожих пробелов

### 12.1. Решение

Рекомендуется минимальная гибридная модель: **внутри системы сохраняются отдельные вопросы-пробелы, а система предлагает группы похожих вопросов для подтверждения владельцем БЗ**.

Это лучше, чем простой счетчик похожих вопросов:

- владелец БЗ видит одну проблему и ее масштаб, а не десятки повторяющихся строк;
- можно закрыть все вопросы группы одним действием;
- каждый исходный вопрос остается доступен для проверки и аудита;
- ошибочную связь можно удалить без удаления события;
- при ошибке группировки вопросы остаются в общем списке и могут обрабатываться по одному;
- аналитика разделяет количество реальных проблем и количество обращений.

Папка не является самостоятельным пробелом и не заменяет `knowledge_gaps`. Это проекция над ними. Предложение группы создается только при наличии минимум двух активных вопросов с высоким векторным сходством. До подтверждения владельцем оно не используется для массового закрытия. Одиночный вопрос отображается как обычный пробел.

### 12.2. Сравнение вариантов

| Вариант | Плюсы | Риски | Решение |
| --- | --- | --- | --- |
| Счетчик похожих вопросов у каждой строки | Минимальные изменения UI и API; безопасный fallback | Владелец все равно работает с длинным списком; не видно границ проблемы и состава группы; массовое закрытие требует отдельного выбора | Использовать как атрибут группы и метрику, но не как основной UX |
| Группы-кандидаты | Снижает визуальный шум; дает владельцу контроль; поддерживает массовое закрытие после проверки | Требует одного действия подтверждения | Рекомендуемый MVP |
| Только папки без исходных вопросов | Самый простой экран | Нельзя проверить ошибочную классификацию и восстановить отдельное решение; риск потери контекста | Не использовать |

### 12.3. Источник сходства

1. Сразу после успешного `record_gap` запускается группировка для нового или обновленного пробела. Ошибка embedding или группировки не отменяет сохранение пробела.
2. Для каждого пробела используется `resolved_query`. Если он пуст, используется нормализованный `raw_question`.  
3. Нормализация выполняется существующим `_normalise`: регистр, `ё/е`, пунктуация и пробелы. Исходный текст не изменяется.
4. Нормализованный текст векторизуется тем же embedding-сервисом, который уже используется системой. В `knowledge_gaps` сохраняются вектор, модель и размерность.
5. Сходство считается косинусным (`1 - embedding <=> embedding`) в PostgreSQL/pgvector.
6. Для MVP достаточно искать кандидатов по векторному порогу. Вопросы с высокой близостью предлагаются владельцу БЗ; автоматический LLM-классификатор объекта и намерения не является обязательным.
7. Владелец проверяет смысл вопросов перед подтверждением. Например, «Состав ОАК» и «Стоимость ОАК» могут иметь высокое сходство из-за общего объекта, но должны быть разделены как разные пробелы.

Порог сходства задается настройкой, а не зашивается в код. Начальное значение для пилота необходимо проверить на реальных данных; ошибочное объединение опаснее, чем отсутствие объединения.

### 12.4. Правила формирования группы

- Группировка выполняется сразу после успешного `record_gap`. Для учебного проекта отдельная очередь или worker не требуются.
- Новый пробел сравнивается только с активными группами и активными пробелами той же БЗ.
- Если похожих пробелов нет, вопрос остается одиночным.
- При первой найденной паре создается новая группа-кандидат.
- Если вопрос подходит к нескольким группам, он добавляется в группу с максимальным similarity.
- В одну группу можно добавить неограниченное количество пробелов.
- Владелец подтверждает предложение целиком или выбирает конкретные вопросы; только подтвержденные связи становятся рабочей группой.
- Группа получает заголовок из наиболее частого/репрезентативного `resolved_query`. Заголовок можно изменить вручную.
- Подтвержденная группа появляется в начале списка только при `active_member_count >= 2`; предложения показываются отдельно и не доступны для массового закрытия.
- Внутри группы показываются все вопросы, частота каждого, даты первого/последнего появления, причина и статус.
- Вопрос может состоять только в одной активной группе. При отвязке связь помечается удаленной, исходный пробел остается открытым и снова показывается как одиночный. Для этой пары сохраняется запрет повторной автоматической рекомендации без нового ручного подтверждения.
- Закрытые/отклоненные пробелы не должны автоматически открывать группу. Новый такой же вопрос создает новую открытую попытку и может быть включен в существующую группу только после подтверждения владельцем БЗ.

### 12.5. Модель данных

Добавляются сущности поверх текущей `knowledge_gaps`:

```sql
CREATE TABLE knowledge_gap_groups (
    id BIGSERIAL PRIMARY KEY,
    title TEXT NOT NULL,
    representative_query TEXT NOT NULL,
    status TEXT NOT NULL DEFAULT 'candidate'
        CHECK (status IN ('candidate', 'open', 'in_review', 'resolved', 'dismissed')),
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    resolved_at TIMESTAMPTZ NULL
);

CREATE TABLE knowledge_gap_group_members (
    group_id BIGINT NOT NULL REFERENCES knowledge_gap_groups(id) ON DELETE CASCADE,
    gap_id BIGINT NOT NULL REFERENCES knowledge_gaps(id) ON DELETE CASCADE,
    similarity REAL NOT NULL,
    assignment_source TEXT NOT NULL
        CHECK (assignment_source IN ('candidate', 'owner_confirmed')),
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    removed_at TIMESTAMPTZ NULL,
    removed_by TEXT NULL,
    removal_reason TEXT NULL,
    PRIMARY KEY (group_id, gap_id)
);

CREATE UNIQUE INDEX knowledge_gap_group_members_active_gap_idx
    ON knowledge_gap_group_members (gap_id)
    WHERE removed_at IS NULL;
```

Для `knowledge_gaps` добавляются `embedding`, `embedding_model` и индекс HNSW. Если размерность модели отличается от текущей, используется отдельная колонка/индекс или отдельная миграция, а не неявное приведение вектора. Вектор группы в MVP не хранится: группа формируется из выбранных пробелов.

Ограничения уникальности:

- один `gap_id` может иметь только одну активную связь с группой (`removed_at IS NULL`);
- одна пара `group_id` + `gap_id` не может быть добавлена повторно благодаря `PRIMARY KEY (group_id, gap_id)`;
- после отвязки старая связь не удаляется, а сохраняется с `removed_at`, `removed_by` и `removal_reason`.

Статус подтвержденной группы является агрегированным представлением:

- `open`, если есть хотя бы один открытый участник;
- `in_review`, если открытых участников нет, но хотя бы один участник в работе;
- `resolved`, если все участники закрыты;
- `dismissed`, если все участники отклонены.

Перевод группы в `resolved` не удаляет участников и не скрывает историю. При массовом закрытии на каждый участник записываются `resolved_at`, автор и общий комментарий в аудит.

### 12.6. API и интерфейс

Добавляются:

- `GET /api/v1/knowledge-gap-groups` — подтвержденные группы и предложения группировки; по умолчанию сначала подтвержденные группы, затем одиночные пробелы;
- `GET /api/v1/knowledge-gap-groups/{group_id}` — группа, состав участников и метаданные сходства;
- `POST /api/v1/knowledge-gap-groups/{group_id}/confirm` — подтверждает предложение целиком или переданный список участников;
- `POST /api/v1/knowledge-gap-groups/{group_id}/resolve` — транзакционно закрывает выбранных или всех активных участников;
- `POST /api/v1/knowledge-gap-groups/{group_id}/members/{gap_id}/detach` — отвязывает участника с обязательной причиной;
- `PATCH /api/v1/knowledge-gaps/{gap_id}` сохраняется для индивидуальной работы;

Операция массового закрытия принимает `member_ids`, `note`, `author` и `idempotency_key`. При отсутствии `member_ids` явно означает «все активные участники» только после подтверждения UI. Ответ содержит число успешно закрытых участников и список ошибок; частичное успешное выполнение не маскируется.

В UI:

1. в начале списка отображаются подтвержденные группы с бейджем количества активных вопросов и обращений;
2. одиночные пробелы отображаются ниже в существующей таблице;
3. открытие папки показывает заголовок, репрезентативный вопрос, состав, частоты, сходство и кнопку «Закрыть все»;
4. перед массовым закрытием показываются количество участников и список вопросов, а комментарий обязателен;
5. у каждого участника есть «Отвязать от группы»;
6. предложения группировки показываются в отдельном блоке «Требует проверки» и не включаются в рабочую группу до подтверждения;
7. при ошибке загрузки/сохранения UI показывает ошибку и не выдает ложное подтверждение.

### 12.7. Надежность, безопасность и rollout

- Сначала успешно завершается `record_gap`, затем сразу запускается группировка. Сбой embedding или группировки не отменяет создание пробела.
- Повторная обработка события идемпотентна по `gap_id` и модели embedding; ограничения БД не позволяют создать повторное активное членство.
- Для учебного проекта отдельная очередь или worker не требуются.
- Доступ к группам наследует ролевые ограничения карты пробелов. В embedding нельзя включать ФИО, номер карты и другие лишние персональные/медицинские данные.
- Логируются `gap_id`, `group_id`, similarity, модель/версия embedding, источник решения, действие отвязки и результат массового закрытия.
- При обновлении embedding-модели выполняется фоновая переиндексация предложений; подтвержденные группы и ручные отвязки не должны быть перезаписаны.

Метрики качества: доля подтвержденных предложений, доля ручных отвязок, среднее число участников группы, доля закрытий через группы, время группировки и число повторно открытых пробелов.

## 13. Критерии приемки MVP

1. Уточняющий вопрос сохраняет `raw_question` и получает `resolved_query` с учетом `conversation_id`.
2. При недостаточности корпоративной БЗ создается ровно одна автоматическая запись на `query_id`, даже если затем используется Web Search.
3. При отрицательной оценке можно выбрать причину и отправить ее вместе с `query_id`.
4. `no_knowledge_base_answer` создает запись в `knowledge_gaps`.
5. `answer_formatting`, `wrong_context`, `answer_irrelevant` и `technical_error` не создают пробел автоматически и маршрутизируются как проблемы качества.
6. Нельзя создать feedback для неизвестного `query_id`.
7. Повторная отправка одного feedback не создает дублирующее событие.
8. Внешний ответ помечается как внешний и не записывается в БЗ автоматически.
9. В административной выборке видны исходный вопрос, нормализованный запрос, причина, источник события, статус и дата.
10. При сбое сохранения пользователь видит ошибку, а не ложное подтверждение.
11. После успешного `record_gap` запускается группировка; ошибка группировки не отменяет создание пробела.
12. Два пробела с векторами выше порога формируют предложение группы, а одиночный пробел не отображается как папка.
13. Если вопрос подходит к нескольким группам, он добавляется в группу с максимальным similarity.
14. Владелец БЗ может подтвердить предложение целиком или выбрать только часть участников.
15. Только подтвержденная группа из минимум двух активных участников отображается выше одиночных пробелов.
16. В карточке группы видны все участники, частоты, similarity и текущие статусы.
17. Отвязка участника сохраняет исходный пробел, аудит действия и возвращает его в список одиночных пробелов.
18. Один `gap_id` не имеет более одной активной связи с группой.
19. Одна пара `gap_id` + `group_id` не добавляется повторно.
20. Для отвязанной пары сохраняется запрет повторной автопредлагаемой связи без ручного подтверждения.
21. Массовое закрытие меняет статус только выбранных активных участников, сохраняет общий комментарий и не удаляет историю.
22. При ошибке embedding или группировки пробел остается доступным для индивидуальной обработки.

## 14. Решения, которые нужно подтвердить до разработки

1. Кто имеет право видеть все пробелы и переводить их в `resolved`: заведующий, редактор БЗ или отдельная роль?
2. Нужно ли создавать пробел по `knowledge_incomplete` сразу или сначала требовать обязательный комментарий регистратора?
3. Должна ли автоматическая запись создаваться для каждого `query_id` или в пределах короткого окна нужна дедупликация одинакового `resolved_query`? Для предложенной первой итерации выбран вариант «каждый `query_id` отдельно».
4. Нужен ли регистратору видимый статус «вопрос передан на доработку», или достаточно общего подтверждения?
5. Должен ли Web Search оставаться включенным при автоматической фиксации пробела во всех сценариях?
6. Какой порог сходства использовать для формирования предложений после проверки на реальных данных?
7. Нужна ли владельцу БЗ ручная операция «объединить две группы» или в MVP достаточно подтверждения предложений, отвязки и индивидуального закрытия?
