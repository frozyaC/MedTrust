# Feature: Quick Buttons

## 1. Назначение

Quick Buttons — это компактные кнопки над обычной строкой поиска MedTrust. Они помогают регистратору не печатать часто используемый вопрос вручную.

Нажатие кнопки:

1. подставляет заранее подготовленный текст вопроса в строку поиска;
2. при наличии доступного контекста добавляет параметры текущего приема или пациента;
3. оставляет вопрос доступным для просмотра и редактирования;
4. отправляет его в тот же поиск, который используется для любого ручного запроса.

Quick Buttons не являются отдельным поиском, отдельным режимом ответов, каталогом медицинских сценариев или механизмом маршрутизации. Они не меняют Retrieval/RAG, проверку достаточности контекста, генерацию ответа, Safety / Guardrails и правила показа источников.

## 2. Пример пользовательского сценария

Регистратор открыл карточку пациента с записью на УЗИ органов брюшной полости и нажал кнопку `Как подготовиться к этому исследованию?`.

В строку поиска подставляется, например:

> Как подготовиться к УЗИ органов брюшной полости в рамках текущей записи?

Регистратор может изменить формулировку или добавить уточнение, затем запускает обычный поиск. Ответ формируется стандартным контуром MedTrust по базе знаний, контексту и действующим ограничениям.

Если контекст не определен, кнопка подставляет общий вопрос без догадок, например `Как подготовиться к исследованию {название}?`, где `{название}` остается для уточнения регистратором.

## 3. Что входит в фичу

| Входит | Не входит |
| --- | --- |
| Набор коротких вопросов, утвержденных владельцем базы знаний | Отдельный алгоритм поиска или отдельная база ответов |
| Подстановка вопроса в существующее поле поиска | Автоматический запуск другого пайплайна обработки |
| Подстановка известных параметров текущего приема | Самостоятельное определение диагноза, показаний или противопоказаний |
| Возможность отредактировать вопрос перед отправкой | Автоматическое назначение исследования или лечения |
| Статистика нажатий и фактических запросов для подбора кнопок | Гарантия, что по каждому вопросу есть ответ в БЗ |

Кнопка должна оставаться полезной и при отсутствии карточки пациента: в этом случае она просто подставляет общий текстовый шаблон.

## 4. Требования к формулировке кнопок

Хорошая кнопка:

- соответствует частому вопросу регистратора или пациента;
- короткая и понятная без инструкции;
- не содержит ответа и не обещает результат;
- допускает подстановку контекста приема, но не требует передачи лишних данных;
- ведет к поиску в существующей базе знаний;
- не подменяет медицинское решение формулировкой вопроса.

Контекст добавляется только из доступных и необходимых данных: тип услуги, специалист, филиал, дата или статус записи. ФИО, номер карты, телефон, диагнозы, аллергии, беременность, хронические заболевания и лекарства не подставляются в текст кнопки по умолчанию.

Если для ответа может понадобиться чувствительный медицинский контекст, кнопка должна формулировать вопрос для поиска, а не превращаться в персональную рекомендацию. Например, `Что нужно уточнить у медицинского работника перед процедурой?`, а не `Есть ли у пациента противопоказания?`.

## 5. Кандидаты кнопок для пилота

Ниже приведены кандидаты, отобранные по сценариям в `knowledge-base/Регистратура`. Они являются вопросами для подстановки, а не фиксированными ответами. Перед включением в интерфейс частотность нужно подтвердить логами обращений и пилотом.

### 5.1. Прием и запись

| Текст кнопки | Возможный контекст |
| --- | --- |
| `Как подготовиться к первичному приему к {специалисту}?` | Специалист, тип приема |
| `Как подготовиться к повторному приему к {специалисту}?` | Специалист, тип приема |
| `Что взять с собой на прием к {специалисту}?` | Специалист, филиал, тип приема |
| `Какие документы нужны для этого визита?` | Первичный/повторный визит, филиал |
| `Нужно ли уточнить причину обращения перед записью к {специалисту}?` | Специалист |
| `Куда записать пациента с этой причиной обращения?` | Специалист, причина обращения, тип записи |
| `Как подтвердить эту запись и что будет при недозвоне?` | Специалист, количество записей, статус контроля |

Последняя кнопка должна приводить к обычному поиску по правилам обзвона. Она не должна сама звонить, отправлять СМС или менять запись.

### 5.2. Процедуры и подготовка

| Текст кнопки | Возможный контекст |
| --- | --- |
| `Как подготовиться к {процедуре}?` | Название услуги |
| `Что нужно уточнить перед записью на {процедуру}?` | Название услуги, тип записи |
| `Нужно ли назначение врача для {процедуры}?` | Процедура, наличие назначения |
| `Какие ограничения действуют перед {процедурой}?` | Процедура |
| `В каком порядке пройти эти исследования?` | Набор услуг в текущей записи |
| `Можно ли проводить эту процедуру после другого исследования?` | Процедуры и дата приема |

Кнопки из этой группы не должны просить модель определить индивидуальные противопоказания или подобрать исследование по симптомам. Если в базе есть только правило о назначении врача, поиск должен вернуть это правило и соответствующий скрипт.

### 5.3. Анализы и результаты

| Текст кнопки | Возможный контекст |
| --- | --- |
| `Как подготовиться к этому анализу?` | Название анализа |
| `Какой срок готовности у этого анализа?` | Название анализа, лаборатория |
| `Почему результат этого анализа может задержаться?` | Название анализа |
| `Как получить результат этого анализа?` | Пациент/доверенное лицо, тип результата |
| `Кому можно выдать результат и какие документы нужны?` | Получатель, тип результата |
| `Можно ли прокомментировать результат пациенту?` | Тип результата |
| `Можно ли добавить это исследование к уже взятой крови?` | Исходный анализ, запрошенное дополнительное исследование |

Кнопка `Какой срок готовности у этого анализа?` подходит для пилота только там, где срок действительно описан в БЗ. Если срок для выбранного анализа не найден, обычный поиск должен показать недостаток данных, а не сгенерировать оценку.

### 5.4. Маршрутизация по типовым обращениям

| Текст кнопки | Возможный контекст |
| --- | --- |
| `Куда записать пациента с травмой, полученной {срок назад}?` | Давность травмы, факт обращения в другой клинике |
| `Принимает ли травмпункт такую травму?` | Вид травмы |
| `Куда направить пациента после укуса клеща?` | Возраст, наличие острых симптомов |
| `Куда направить вопрос по готовности лабораторного результата?` | Вид анализа, время обращения |
| `Какой скрипт использовать при претензии пациента?` | Тема претензии |

Такие вопросы ускоряют ввод, но не принимают решение вместо регистратора или медицинского работника. Контекст нужен для уточнения запроса и поиска релевантной статьи, а не для автоматического назначения маршрута.

## 6. Что нельзя использовать как кнопку

Нельзя добавлять кнопки, которые сами по себе формулируют медицинское решение:

- `Какой диагноз у пациента?`;
- `Расшифровать анализ и определить, опасно ли это`;
- `Какие лекарства принимать и в какой дозировке?`;
- `Можно ли отменить или заменить препарат?`;
- `Есть ли у пациента противопоказания?`;
- `Какое исследование выбрать без назначения врача?`;
- `Можно ли не вызывать скорую помощь?`.

Безопаснее использовать вопрос, ускоряющий поиск регламента: `Какой скрипт использовать при вопросе о результате?`, `К кому передать медицинский вопрос?`, `Какие документы нужны для записи по уже имеющемуся назначению?`.

## 7. Контекст и защита данных

Quick Buttons не расширяют права MedTrust на обработку данных. Подстановка контекста должна подчиняться тем же ролевым ограничениям и требованиям минимизации, что и ручной поиск.

Правила:

1. Сначала использовать контекст приема и услуги, поскольку он обычно достаточен для организационного вопроса.
2. Не добавлять в поисковый текст идентификаторы пациента.
3. Чувствительные сведения о здоровье не подставлять автоматически, если они не нужны для конкретного поиска.
4. Перед отправкой показывать регистратору итоговый текст вопроса.
5. При неполном контексте оставить вопрос редактируемым и не делать догадок.
6. Применять к отправленному вопросу обычные проверки безопасности, источников, достаточности данных и врачебной тайны.

## 8. Метрики

Quick Buttons оцениваются как улучшение ввода, а не как отдельный механизм качества ответа:

- время от открытия поиска до отправки вопроса;
- доля запросов, отправленных после нажатия кнопки;
- доля отредактированных подстановок;
- доля повторных ручных переформулировок после нажатия;
- время от отправки вопроса до получения ответа;
- оценка полезности ответа и доля запросов без достаточного источника;
- частота использования каждой кнопки.

Успехом считается сокращение времени формулировки запроса без роста медицинских ошибок, пустых запросов и лишней передачи данных.

## 9. Открытые решения для пилота

- где хранить каталог формулировок: конфигурация продукта или база знаний;
- кто утверждает, изменяет и отзывает кнопки;
- показывать ли кнопки глобально или только при наличии соответствующего контекста приема;
- какие поля можно безопасно подставлять автоматически;
- нужно ли подставлять вопрос сразу при нажатии или сначала оставлять его на подтверждение регистратора;
- какой набор из 10–15 кнопок подтвердить по статистике обращений.
