# Требуемые изменения по безопасности MedTrust

Документ описывает предполагаемые изменения, необходимые для закрытия основных
рисков MVP, зафиксированных в
[architecture_sprint4.md](../architecture_sprint4.md).

## 1. Границы системы и модель угроз

MedTrust разворачивается во внутреннем контуре клиники. Пользовательский
интерфейс, backend и PostgreSQL не должны быть доступны из внешнего Интернета.
Планируемые внешние соединения:

- CRM/АРМ клиники — через защищённый интеграционный шлюз;
- GigaChat API — только для обработки минимально необходимого prompt;
- web search — только через контролируемый шлюз и разрешённые HTTPS-источники.

Внутренняя сеть не считается полностью доверенной. Угрозами считаются
скомпрометированное рабочее место регистратора, украденная учётная запись,
внутренний злоумышленник и ошибочная настройка сети.

SQL injection через RAG-фрагменты не является целевым сценарием: GigaChat не
имеет прямого доступа к PostgreSQL, DB-инструментов и возможности выполнять SQL.
SQL выполняется backend-кодом. При дальнейшей разработке сохраняется обязательное
требование использовать параметризованные запросы.

## 2. Приоритет P0: backend-аутентификация

### Проблема

Сейчас frontend-login является демонстрационным: флаг входа хранится в
`localStorage`, а backend не проверяет пользователя. Любой клиент, имеющий сетевой
доступ к API, потенциально может отправить запрос напрямую.

### Требуемые изменения

1. Подключить корпоративный SSO через OIDC/SAML/LDAP или другой утверждённый
   механизм идентификации.
2. Реализовать серверную сессию или проверку JWT на каждом защищённом маршруте.
3. Убрать доверие к `localStorage` как к признаку авторизации.
4. Добавить короткое время жизни access token, refresh/revocation и logout.
5. Проверять issuer, audience, подпись, срок действия и обязательные claims токена.
6. Не передавать credentials в frontend или GigaChat.
7. Ввести роли:
   - `registrar` — вопросы, доступ к разрешённым пациентам и своим диалогам;
   - `kb_owner` — карта пробелов, feedback и комментарии;
   - `admin` — пользователи, интеграции, reindex и технические настройки.

### Критерий готовности

Запрос без действующей серверной аутентификации получает `401`. Аутентификация
frontend без подтверждения backend не даёт доступа к данным.

## 3. Приоритет P0: закрытие API и RBAC

### Проблема

Сейчас без серверной авторизации доступны запросы, чтение диалогов и документов,
feedback, переиндексация Wiki и изменение карты пробелов.

### Требуемые изменения

Разделить маршруты по ролям:

| Область | Роли |
|---|---|
| `/health` | технический мониторинг, без персональных данных |
| `/query`, `/search`, `/web-search` | `registrar` и разрешённые сотрудники |
| `/conversations/*` | только владелец диалога или разрешённая роль |
| `/feedback` | авторизованный пользователь для доступного `query_id` |
| `/knowledge/reindex` | только `admin`/оператор БЗ |
| `/knowledge-gaps/*`, `/quality-issues/*` | `kb_owner`, `admin` |
| CRM/АРМ endpoints | только доверенный integration gateway |

Дополнительно:

- закрыть PostgreSQL от пользовательских подсетей;
- разместить API за reverse proxy или API gateway;
- разрешить входящие соединения только от frontend, integration gateway и
  технического мониторинга;
- добавить rate limiting и лимиты размера тела запроса;
- вести аудит успешных и отклонённых вызовов;
- не возвращать stack trace, SQL и внутренние адреса клиенту;
- разделить технические и пользовательские ошибки.

### Критерий готовности

Каждый маршрут имеет явное требование роли. Попытка регистратора вызвать reindex
или изменить статус пробела получает `403`. Прямое подключение к PostgreSQL из
пользовательской сети невозможно.

## 4. Приоритет P0: доступ к чужим пациентам и диалогам

### Проблема

Одного `conversation_id`, `query_id` или `patient_id` недостаточно для проверки
права доступа. Идентификатор может быть передан вручную через API.

### Требуемые изменения

1. Добавить в модель данных владельца и область доступа:
   - `owner_user_id` или `created_by`;
   - `clinic_id`/`organization_id`;
   - при необходимости `patient_id` и источник пациента.
2. На backend проверять право пользователя до чтения, изменения или добавления
   сообщения.
3. Проверять, что выбранный пациент доступен пользователю в CRM/АРМ или в
   разрешённой локальной области.
4. Не принимать права доступа из frontend-полей.
5. Не позволять использовать чужой `conversation_id` для продолжения диалога.
6. Не включать в ответ больше данных, чем необходимо текущему сценарию.
7. Предпочитать передачу минимального онлайн-контекста из CRM/АРМ без хранения
   полного профиля в MedTrust.
8. Если применяются регулярные выгрузки, добавить:
   - версию и источник записи;
   - дату синхронизации;
   - правила удаления устаревших пациентов;
   - контроль расхождений и аудит выгрузки.

### Критерий готовности

Пользователь не может прочитать или продолжить чужой диалог, даже если знает его
идентификатор. Доступ к пациенту определяется сервером и правами пользователя.

## 5. Внешний egress: GigaChat и web search

### GigaChat API

- разрешить исходящие соединения только к утверждённым endpoint;
- использовать TLS certificate verification;
- хранить credentials в secret manager;
- ротировать ключи и ограничить их права;
- согласовать с провайдером режим хранения, обучения и журналирования запросов;
- передавать обезличенный и минимальный контекст;
- при запрете вывода patient context за пределы клиники использовать локальную
  модель или внутренний LLM-шлюз.

### Web search

- направлять web-запросы через отдельный SearXNG/API gateway;
- разрешать только HTTPS и домены из allowlist;
- запрещать loopback, private IP, metadata endpoint и `file:` URL;
- ограничить таймаут, размер ответа, число redirects и число источников;
- очищать HTML и не исполнять скрипты внешней страницы;
- хранить URL и статус источника, но не сохранять внешнюю страницу без необходимости.

## 6. Защита хранения и журналирования

Шифрование PostgreSQL и резервных копий необходимо, но не заменяет
аутентификацию и проверки доступа.

Нужно:

- использовать отдельного DB-пользователя с минимальными правами;
- запретить прямой доступ к БД из пользовательской сети;
- хранить ключи шифрования отдельно от backup;
- шифровать Docker volumes и резервные копии;
- установить срок хранения сообщений и patient context;
- автоматически удалять или обезличивать устаревшие данные;
- маскировать PII и токены в application logs, trace и error details;
- вести неизменяемый audit log доступа к пациенту, диалогу, источникам и
  административным операциям;
- регулярно проверять backup restore и отзыв скомпрометированных credentials.

## 7. План реализации

### Этап 1 — блокирующие меры до внутренней эксплуатации

- backend-аутентификация;
- RBAC и защита всех маршрутов;
- ownership/scope для пациентов и диалогов;
- закрытие PostgreSQL и API сетевыми правилами;
- secret manager и TLS certificate verification;
- минимизация и маскирование patient context;

### Этап 2 — интеграционная безопасность

- защищённый CRM/АРМ gateway;
- mTLS или подпись запросов;
- nonce/timestamp и idempotency;
- аудит и контроль версий выгрузок;
- политика удаления и сверки данных.

### Этап 3 — проверка и сопровождение

- тесты на обход ролей и IDOR;
- тесты утечки PII в prompt, ответах и логах;
- тесты сетевой изоляции и egress allowlist;
- регулярное обновление зависимостей и security review;
- план реагирования на инциденты и ротации секретов.

## 8. Итоговая целевая схема

```text
Рабочее место регистратора
        │ SSO/session + RBAC
        ▼
Frontend → API Gateway → MedTrust backend
                            ├─ authorization + ownership checks
                            ├─ PostgreSQL (закрытый сегмент)
                            ├─ CRM/АРМ gateway (mTLS/signature)
                            └─ Egress gateway
                                 ├─ GigaChat API (минимальный обезличенный prompt)
                                 └─ SearXNG → allowlisted HTTPS sources
```

Система считается готовой к внутренней эксплуатации только после закрытия P0:
backend-аутентификации, RBAC, проверки доступа к пациентам/диалогам и защиты
внешнего prompt-контракта. Нахождение компонентов во внутренней сети и
шифрование базы сами по себе не являются достаточной защитой персональных данных.
