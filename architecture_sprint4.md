# MedTrust — архитектура и суть продукта (Sprint 4)

> Документ предназначен как быстрый вход для разработчика или AI-агента. Он фиксирует
> бизнес-назначение, границы ответственности компонентов, реальные потоки данных и
> ограничения текущей реализации. Описания основаны на исходниках репозитория и не
> предполагают наличие скрытого production-контура.

## 1. Краткое резюме

MedTrust — внутренний интеллектуальный справочник для сотрудников регистратуры
клиники или больницы. Регистратор должен быстро ответить пациенту на вопрос о
процедуре, подготовке, документах, филиале, маршрутизации, условиях услуги или
другом организационном правиле, не открывая вручную десятки страниц Wiki и не
выдумывая сведения.

Система решает задачу через гибридный RAG:

1. корпоративная Wiki импортируется из ZIP-архива Markdown-документов;
2. документы разбиваются на смысловые фрагменты с сохранением пути Wiki;
3. для фрагментов строятся embeddings и полнотекстовые индексы PostgreSQL;
4. вопрос регистратора ищет релевантные фрагменты одновременно семантически,
   лексически и по пути Wiki;
5. найденные источники, профиль пациента и ограниченная история диалога передаются
   GigaChat;
6. ответ возвращается с цитатами и карточками источников;
7. если локальной доказательной базы недостаточно, система либо выполняет
   контролируемый поиск по внешним медицинским сайтам, либо честно сообщает о
   недостатке подтверждения;
8. отрицательная оценка и автоматическая диагностика недостатка знаний превращаются
   в записи карты пробелов, которую владелец базы знаний обрабатывает в админке.

Главная бизнес-ценность — не «медицинский чат-бот», а быстрый и проверяемый
операционный помощник регистратора, который отвечает по правилам конкретной
организации, показывает основания ответа и замыкает цикл улучшения базы знаний.

## 2. Для кого и зачем

### Основные пользователи

- **Регистратор** — задаёт вопросы от имени пациента, выбирает пациента и видит
  короткий ответ с источниками, предупреждениями и возможностью оценить качество.
- **Владелец базы знаний / сотрудник клиники** — просматривает пробелы, меняет их
  статусы, оставляет комментарии, подтверждает или закрывает группы похожих
  запросов.
- **Разработчик/оператор** — переиндексирует Wiki, проверяет технические проблемы
  качества и состояние backend.

### Типовые вопросы

- как подготовиться к гастроскопии, КТ, МРТ, УЗИ, анализу;
- можно ли есть, пить, курить или принимать лекарства перед процедурой;
- какие документы нужны, где расположен кабинет, как работает филиал;
- какие условия и ограничения указаны в правилах клиники;
- какие внешние/актуальные клинические рекомендации подтверждаются авторитетными
  источниками.

### Что система принципиально не должна делать

- не заменяет врача и не принимает клиническое решение;
- не придумывает расписание, цену, внутренний регламент или доступность записи;
- не назначает лечение, дозировки или отмену препаратов;
- не переносит факты и пациента из предыдущего диалога на новый запрос;
- не выдаёт общую память модели за подтверждённое правило клиники.

Эти ограничения сформулированы в системном prompt GigaChat и дополнительно
поддерживаются проверками релевантности, безопасности и достаточности доказательств.

## 3. Архитектурная схема

```text
┌──────────────────────────────┐
│ React/TypeScript frontend     │
│ Регистратор + Admin gaps UI   │
└──────────────┬───────────────┘
               │ HTTP /api/v1
┌──────────────▼───────────────┐
│ FastAPI backend               │
│ routes → services → repos    │
└───────┬──────────┬───────────┘
        │          │
        │          ├──────────────► GigaChat API
        │          └──────────────► Embedding API (OpenAI-compatible)
        │
        ▼
┌──────────────────────────────┐
│ PostgreSQL 16 + pgvector      │
│ Wiki, chunks, chats, feedback │
│ gaps, events, quality issues  │
└──────────────┬───────────────┘
               │
               └──────────────► SearXNG → allowlisted HTTPS sources
```

### Слои backend

- `app/main.py` — создание FastAPI-приложения, CORS, startup-инициализация БД и
  первичный seed индекса.
- `app/api/routes.py` — HTTP-контракт и преобразование исключений в HTTP-ошибки.
- `app/schemas/api.py` — Pydantic-модели входных запросов и перечисления статусов.
- `app/services/` — бизнес-логика: RAG, контекст, GigaChat, web search, ingestion,
  память, feedback и карта пробелов.
- `app/db/database.py` — подключение PostgreSQL и базовая DDL-схема.
- `app/db/repository.py` — операции над документами, чанками и feedback.
- `app/db/seed.py` — автоматическая загрузка архива, заданного в настройках.

Frontend не является серверным шаблоном: это отдельное React-приложение, которое
вызывает REST API через `fetch`. Основная страница и админская страница выбираются
в `frontend/src/main.tsx` по URL-пути.

## 4. Сквозной пользовательский сценарий: вопрос регистратора

### 4.1. Frontend

1. Регистратор выбирает пациента в боковой панели или работает без
   персонализации.
2. `ChatComposer`/поисковая панель формирует вопрос.
3. `frontend/src/api/query.ts` преобразует карточку пациента:
   - возраст и пол передаются напрямую;
   - аллергии объединяются с противопоказаниями;
   - хронические состояния объединяются в `anamnesis`.
4. Клиент отправляет `POST /api/v1/query` с `question`, `top_k`,
   `patient` и, если есть, `conversation_id`.
5. Ответ преобразуется в `AnswerData`: текст, источники, цитаты, `query_id`,
   флаги `wikiStrongMatch`, `noAnswer` и `webSearchUsed`.
6. `AnswerBlock` отображает ответ в Markdown, цитаты `[W1]`/`[WEB1]`, предупреждение
   об отсутствии сильного совпадения и кнопку feedback.

Состояния интерфейса включают загрузку, обычный ответ, отсутствие ответа,
конфликт/предупреждение и ошибку. История conversation ID сохраняется в
`localStorage`, чтобы браузер мог восстановить связь с backend-диалогом.

### 4.2. Backend pipeline

`RagService.answer()` — центральный orchestration-слой. Упрощённая последовательность:

1. Нормализуется вопрос и определяется, является ли он новым вопросом,
   уточнением или просьбой отредактировать прошлый ответ.
2. Для follow-up используется `ConversationMemory` и
   `LLMContextualizer`. Контекстуализатор выдаёт ограниченный JSON с intent,
   resolved query, сущностями и уровнем уверенности. При неоднозначности система
   может вернуть уточняющий вопрос, а не угадывать объект.
3. Выполняется разбиение составного вопроса на аспекты: например, подготовка к
   нескольким процедурам ищется отдельными запросами.
4. `KnowledgeRepository.hybrid_search()` получает embedding запроса и объединяет:
   - dense ranking по cosine distance;
   - PostgreSQL Russian FTS по `search_vector`;
   - отдельный ranking по `path_vector`, чтобы учитывать иерархию Wiki.
5. Рейтинги объединяются weighted Reciprocal Rank Fusion. По умолчанию веса:
   dense `1.0`, lexical `1.0`, path `1.25`.
6. `source_relevance` оценивает достаточность источников для конкретного аспекта.
   Проверяется, например, что общий текст про анализ крови не ошибочно используется
   как инструкция для КТ или гастроскопии.
7. Для чувствительных вопросов проверяется наличие специального подтверждения:
   лекарства, аллергии, антикоагулянты, беременность, хронические заболевания,
   противопоказания.
8. При необходимости запускается web fallback. Источники проходят проверки домена,
   темы и типа доказательств.
9. GigaChat получает системные правила, вопрос, профиль пациента, ограниченную
   историю и отобранные источники. Ответ обязан сохранять смысл источников и
   цитировать их.
10. Ответ форматируется: нормализуются списки, сохраняются метки источников,
    формируется safe no-evidence response для неподтверждённых внутренних правил.
11. Сообщения пользователя и ассистента сохраняются в conversation. Результат
    answerability и диагностические поля сохраняются для последующей карты пробелов.

### 4.3. Редактура предыдущего ответа

Запросы вроде «сократи ответ», «переформулируй» или «сделай вежливее» распознаются
отдельно. Они не запускают новый поиск и не должны добавлять фактов: GigaChat
редактирует последний ответ ассистента, сохраняя условия, числа и цитаты.

## 5. Поиск по корпоративной Wiki

### 5.1. Интеграция и ingestion

Источник индекса — ZIP с Markdown-файлами (`data/sample_sufler.zip`, сейчас
содержит 27 записей). Каждый документ должен иметь обязательную строку:

```text
Путь: Раздел/Подраздел/Статья
```

Опционально распознаются `URL:`, `Источник:` или `Source-URL:`. `ingestion.py`:

- нормализует разделители и путь;
- извлекает заголовок из Markdown;
- удаляет строку `Путь:` из содержимого;
- делит текст по заголовкам Markdown;
- режет длинные секции на чанки;
- добавляет к embedding-тексту путь, название, раздел и содержимое.

Размер чанка по умолчанию — 2200 символов, overlap — 250 символов. UUID
документа и чанка детерминированы через UUID5 от пути и индекса, что обеспечивает
стабильные идентификаторы при повторной индексации.

### 5.2. Переиндексация

`POST /api/v1/knowledge/reindex` принимает ZIP. `KnowledgeRepository.reindex()`:

1. разбирает все Markdown;
2. строит embedding для всех чанков пакетами по 32;
3. транзакционно очищает `knowledge_documents` через `TRUNCATE ... CASCADE`;
4. вставляет документы и чанки;
5. строит PostgreSQL tsvector-поля.

При старте `app.main.startup()` вызывается `seed_knowledge_index()`. Seed сравнивает
хэш архива и не должен повторно пересоздавать неизменившийся индекс.

### 5.3. Почему учитывается путь

Внутренняя Wiki часто содержит одноимённые услуги в разных филиалах или разделах.
Путь — отдельный сигнал поиска, а не декоративное поле. Это снижает риск смешать
условия разных филиалов, процедур или организационных процессов.

## 6. Внешний поиск и доказательства

Локальная Wiki является приоритетным источником для внутренних правил. Внешний
поиск используется только когда:

- включён `WEB_SEARCH_ENABLED`;
- локальных источников недостаточно;
- вопрос требует свежей клинической информации;
- либо пользователь явно нажал ручной web search.

SearXNG работает как локальный агрегатор (`searxng:8080` в Docker или
`127.0.0.1:8080` при запуске на хосте). Backend фильтрует ссылки:

- только HTTPS;
- домены из allowlist: PubMed, WHO, CDC, FDA, EMA, NICE, NHS, Минздрав и др.;
- отдельные домены для погоды и локального поиска заведений;
- совпадение темы и типа требуемого доказательства.

Результат различает `verified`, `unverified` и `supported_candidate`. Неподтверждённая
ссылка может остаться видимой как кандидат, но не должна считаться основанием
утверждения в ответе. Системные лимиты на запрос: до 2 web-источников, до 3 Wiki
источников и ограничение длины текста каждого источника.

Ручной `POST /api/v1/web-search` — отдельная операция. Её результаты не записываются
в корпоративную Wiki.

## 7. Память диалогов

`ConversationMemory` хранит:

- `conversations` — идентификатор, заголовок и временные метки;
- `chat_messages` — роли user/assistant/system, текст, query ID и JSON-источники;
- `conversation_memory` — опциональное LLM-резюме длинного диалога.

При обычном запросе в prompt передаются не все сообщения, а ограниченная история:
по умолчанию до 4 сообщений для RAG-контекста. Общая настройка recent memory —
12 сообщений. Автоматическое summary отключено (`MEMORY_SUMMARY_ENABLED=false`),
хотя код обновления резюме существует и запускается по порогу сообщений.

Память используется для понимания follow-up, но профиль пациента передаётся
отдельно и не должен автоматически переноситься на другую карточку пациента.

## 8. Карта пробелов и feedback-loop

Это второй значимый бизнес-контур продукта: система не только отвечает, но и
помогает улучшать источник знаний.

### Автоматическая регистрация

После `POST /query` `GapMapService.persist_query_result()` сохраняет:

- `query_answerability` — достаточна ли корпоративная БЗ;
- причины недостаточности;
- использованные источники;
- факт web search;
- `knowledge_gap_events` и связанные элементы;
- legacy-проекцию `knowledge_gaps` для совместимости.

Вопросы обезличиваются перед embedding/semantic index:
email, телефоны, даты рождения, ФИО и похожие идентификаторы заменяются
placeholder-ами. При этом исходный контекст диалога хранится отдельно, поэтому
нужно учитывать требования к доступу к conversation-данным.

### Feedback регистратора

`POST /feedback` принимает positive/negative rating, комментарий, reason code и
query ID. Для negative feedback с причиной `no_knowledge_base_answer`,
`knowledge_incomplete` или `knowledge_outdated` создаётся user-feedback gap.
Остальные причины направляются в `quality_issues`: нерелевантный, неверный,
неформатированный ответ, неверный источник, техническая ошибка и т.п.

Idempotency key поддерживается на уровне схемы feedback, чтобы повторная отправка
не создавала дубликаты.

### Управление владельцем БЗ

Админская страница `/admin/knowledge-gaps` показывает:

- фильтр по периоду, статусу, источнику и причине;
- список пробелов и метрики;
- detail panel с событиями и историей статусов;
- комментарии;
- статусы `open`, `in_review`, `resolved`, `dismissed`;
- owner-managed группы похожих пробелов.

Семантическая близость только предлагает кандидата на группировку. Автоматическое
слияние разных вопросов запрещено: группа подтверждается владельцем БЗ через
`/knowledge-gap-groups/{id}/confirm`. Участника можно отсоединить, а группу —
закрыть с обязательной заметкой и idempotency key.

## 9. Модель данных PostgreSQL

### Базовые таблицы

- `knowledge_documents` — исходный документ, путь Wiki, хэш содержимого, URL.
- `knowledge_chunks` — текст чанка, секция, embedding, полнотекстовые и path-векторы.
- `conversations` — диалог.
- `chat_messages` — сообщения и JSON snapshot источников.
- `conversation_memory` — долговременное summary.
- `query_feedback` — оценка ответа.
- `knowledge_index_state` — хэш последнего индексированного архива.

### Контур качества и пробелов

- `knowledge_gaps` — нормализованная частотная проекция вопроса, статус, причина,
  число повторений и Wiki-кандидаты;
- `knowledge_gap_clusters` — семантические кандидаты/кластеры;
- `knowledge_gap_events` — append-only события по конкретному query;
- `knowledge_gap_event_items` — связь события с gap и источниками;
- `knowledge_gap_comments` — комментарии владельца;
- `knowledge_gap_status_history` — история переходов статуса;
- `query_answerability` — диагностика полноты ответа;
- `quality_issues` и `quality_issue_status_history` — проблемы качества ответа.

### Индексы и расширения

Используется `pgvector` с HNSW cosine index. Для текста применяются PostgreSQL
`tsvector` и GIN. Размер vector задаётся `EMBEDDING_DIMENSION` и по умолчанию
равен 1024. Схема создаётся идемпотентно при старте и дополнительно мигрируется
лениво сервисами пробелов.

## 10. REST API

Все маршруты имеют префикс `/api/v1`.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/health` | Проверка backend и PostgreSQL |
| POST | `/query` | RAG-ответ по Wiki/web/GigaChat |
| POST | `/search` | Поиск источников без генерации ответа |
| POST | `/web-search` | Ручной внешний поиск |
| POST | `/knowledge/reindex` | Полная переиндексация ZIP |
| GET | `/knowledge/{id}` | Метаданные документа |
| GET | `/knowledge/{id}/content` | Полное содержимое документа |
| POST | `/conversations` | Создание диалога |
| GET | `/conversations` | Список диалогов |
| GET | `/conversations/{id}` | Диалог и сообщения |
| GET | `/conversations/{id}/messages` | Сообщения с лимитом |
| POST | `/feedback` | Оценка ответа и регистрация gap |
| GET | `/knowledge-gaps` | Список пробелов |
| GET | `/knowledge-gaps/metrics` | Метрики пробелов |
| GET | `/knowledge-gaps/{id}/events` | События gap |
| GET | `/knowledge-gaps/{id}/history` | История статусов |
| PATCH | `/knowledge-gaps/{id}` | Смена статуса |
| POST | `/knowledge-gaps/{id}/comments` | Комментарий |
| GET | `/knowledge-gap-groups` | Группы пробелов |
| GET | `/knowledge-gap-groups/{id}` | Детали группы |
| POST | `/knowledge-gap-groups/{id}/confirm` | Подтверждение группы |
| POST | `/knowledge-gap-groups/{id}/resolve` | Закрытие группы |
| POST | `/knowledge-gap-groups/{group}/members/{gap}/detach` | Отвязка элемента |
| GET | `/quality-issues` | Проблемы качества ответа |
| PATCH | `/quality-issues/{id}` | Смена статуса проблемы |

Pydantic ограничивает длину вопроса, `top_k`, лимиты списков, статусы и некоторые
поля feedback. Ответ `/query` обычно содержит `query_id`, `conversation_id`,
`answer`, `sources` и `answer_review_diagnostics`.

## 11. Frontend-архитектура

Стек: React 19, TypeScript 5.7, Vite, Tailwind CSS 4, `react-markdown`,
`remark-gfm`, `lucide-react`.

### Основная страница

`frontend/src/App.tsx` управляет состоянием приложения:

- текущий пациент;
- threads и conversation IDs;
- отправка вопроса и web search;
- открытие источников;
- feedback;
- демо-состояния;
- локальные настройки популярных вопросов и подсказок.

Основные визуальные зоны:

- `Header` и `ConversationHeader`;
- `Sidebar`/`PatientCard`;
- `ChatComposer`/`SearchBar`;
- `MessageThread`;

## 12. Запуск и инфраструктура

`docker-compose.yml` поднимает четыре сервиса:

- `db` — `pgvector/pgvector:pg16`, PostgreSQL на хостовом порту 5433;
- `api` — Python 3.11, Uvicorn, порт 8000;
- `frontend` — multi-stage Node 22 build и статическая раздача через `serve`,
  порт 5173;
- `searxng` — локальный web-search, порт 8080.

Зависимость запуска: API ждёт healthcheck базы, frontend ждёт healthcheck API.
Backend Dockerfile копирует только `app` и `data`; конфигурация приходит через
`.env`. Frontend получает `VITE_API_BASE_URL` на этапе build.

Минимальные внешние зависимости:

- credentials GigaChat;
- OpenAI-compatible embedding endpoint;
- PostgreSQL с pgvector;
- SearXNG для внешнего поиска.

Секреты не должны попадать в документацию или frontend. В репозитории есть
`.env.withoutkeys` как пример имён настроек без значений ключей.

## 14. Безопасность и приватность: текущий статус

В репозитории присутствует отдельный [SECURITY-REVIEW.md](./SECURITY-REVIEW.md).
Его вывод необходимо считать частью архитектурного контекста, а не исправленной
функциональностью.

Зафиксированные ограничения MVP:

1. Backend-маршруты подключены без серверной аутентификации. CORS не заменяет
   авторизацию, а порт API публикуется Docker-конфигурацией.
2. `/query`, `/search`, web search, reindex, чтение conversations и операции карты
   пробелов доступны без проверки пользователя/роли.
3. Frontend login — демонстрационный: принимаются любые непустые credentials, а
   флаг входа хранится в `localStorage`.
4. `GIGACHAT_VERIFY_SSL` по умолчанию `false`; для production требуется включить
   проверку сертификата.
5. Проверка владельца `conversation_id` и разграничение ролей администратора на
   backend пока не описаны в коде.

Перед публичным размещением обязательны backend-аутентификация, роли/сессии или
JWT, rate limit/квоты, защита reindex/admin endpoints, owner checks для диалогов и
TLS verification. До этого продукт следует рассматривать как внутренний MVP в
доверенной сети.

Приватность частично поддерживается обезличиванием вопросов в semantic gap index,
но полные сообщения, patient context и исходные query-контексты могут храниться в
PostgreSQL. Доступ к БД и резервным копиям должен быть ограничен отдельно.

## 15. Надёжность и обработка ошибок

- Ошибки внешнего поиска возвращаются как `502` для ручного web-search.
- Ошибки RAG и внутренних операций преобразуются в понятные HTTP detail-сообщения;
  в критичных местах backend логирует stack trace.
- Если запись observability/gap metadata не удалась, валидный медицинский ответ
  не выбрасывается: результат получает явный `tracking_status=failed`.
- При отсутствии подтверждённой Wiki-информации UI показывает предупреждение и
  рекомендует уточнить у ответственного специалиста.
- Web source может быть оставлен как unverified candidate, но не должен повышать
  статус подтверждённого доказательства.
- Startup seed ловит ошибку и логирует её, поэтому backend может стартовать
  деградированно; health endpoint отдельно сообщает состояние БД.

6. Запуск: `docker-compose.yml`, backend/frontend Dockerfile и `.env.withoutkeys`.

Если документация расходится с кодом, приоритет имеет код; этот файл следует

## 17. Короткая ментальная модель для нового агента

```text
Регистратор задаёт вопрос
  → backend восстанавливает контекст follow-up
  → ищет по Wiki (dense + FTS + path)
  → проверяет, достаточно ли конкретных доказательств
  → при необходимости ищет по allowlist внешних источников
  → GigaChat формирует короткий ответ с цитатами
  → frontend показывает ответ, источники и предупреждения
  → feedback/answerability создают событие качества
  → владелец БЗ закрывает пробел или дополняет Wiki
  → следующая переиндексация делает знания доступными регистраторам
```

Иными словами, MedTrust — это связка **операционного интерфейса регистратора,
доказательного гибридного поиска, контролируемой генерации и управляемого
улучшения корпоративной базы знаний**, а не автономная медицинская система.

## 18. Статус продукта и интеграция с CRM/АРМ клиники

На текущем этапе MedTrust разрабатывается как **самостоятельный продукт** со
собственным интерфейсом регистратора, backend, базой знаний и операционной базой
данных. Интеграция с CRM клиники или медицинской АРМ в текущем коде ещё не
реализована, но архитектура должна допускать её без обязательного переноса в
MedTrust всей медицинской информации о пациенте.

Предполагаются два режима интеграции:

1. **Онлайн-передача контекста пациента.** CRM/АРМ передаёт в MedTrust только
   минимально необходимый профиль или ссылочный идентификатор пациента при
   открытии рабочего места регистратора. MedTrust использует этот контекст для
   персонализации ответа, а master-данные остаются в CRM/АРМ.
2. **Регулярная выгрузка.** CRM/АРМ периодически выгружает согласованный набор
   пациентов в отдельную базу пациентов MedTrust. В выгрузку должны попадать только
   поля, необходимые для сценариев справочника; состав, формат, периодичность,
   срок хранения и правила удаления должны быть формализованы отдельно.

Предпочтительный вариант для минимизации риска — онлайн-передача минимального
контекста без постоянного хранения в MedTrust. Регулярная выгрузка может быть
оправдана для автономной работы, но создаёт вторую копию персональных данных,
которую нужно синхронизировать, защищать и удалять при изменении источника.

Интеграционный слой должен быть отдельным от LLM/RAG-логики и включать
аутентификацию систем, проверку схемы и владельца идентификатора пациента,
журналирование обращений, обработку ошибок синхронизации, версионирование
контрактов и явную политику минимизации данных.

## 19. Безопасность внутреннего контура и защита от проникновения

Развёртывание внутри сети клиники снижает экспозицию в Интернет, но **не делает
систему доверенной автоматически**. Угроза может исходить от скомпрометированного
рабочего места регистратора, соседнего сервиса внутренней сети, украденной
учётной записи, ошибочной настройки firewall или вредоносного содержимого,
поступившего из CRM, Wiki, web search или пользовательского запроса.

### Защита персональных данных

Пароль или шифрование только PostgreSQL **недостаточны**. Они защищают главным
образом данные «на диске» или доступ к БД без ключа, но не защищают:

- уже авторизованный или скомпрометированный backend;
- API, доступный из внутренней сети;
- данные в памяти процесса, логах, trace и сообщениях об ошибках;
- резервные копии, Docker volumes и выгрузки;
- персональные данные в frontend/localStorage;
- несанкционированный доступ сотрудника к чужому пациенту;

- скомпрометированные ключи шифрования.

Нужна защита в несколько слоёв:

- сегментация сети: frontend/backend/БД/CRM и внешние шлюзы в отдельных зонах;
- запрет прямого доступа пользователей к PostgreSQL, доступ к БД только от backend;
- backend-аутентификация, SSO или корпоративные сессии, RBAC и проверка владельца
  пациента/диалога на каждом маршруте;
- mTLS или другой взаимный контроль для CRM/АРМ-интеграции;
- TLS внутри сети, включая соединения с CRM и БД, если это поддерживается;
- шифрование БД, дисков и резервных копий с хранением ключей отдельно;
- секреты в secret manager, а не в `.env`, образах или frontend;
- минимизация полей, псевдонимизация, сроки хранения и автоматическое удаление;
- аудит доступа к пациенту, запросов, ответов, выгрузок и административных действий;
- маскирование персональных данных в логах и запрет отправки PII в сторонние LLM/web
  сервисы без отдельного разрешённого режима и договора обработки данных;
- резервное копирование, ротация ключей, отзыв учётных данных и план реагирования.

### Реальные риски MVP

SQL injection через RAG-фрагменты не относится к актуальному сценарию этой
архитектуры: GigaChat не имеет прямого доступа к PostgreSQL, не получает DB-инструмент
и возвращает только текст. SQL выполняется заранее написанным backend-кодом, а
извлечённые значения передаются драйверу параметрами. Это не отменяет обычное
требование сохранять параметризованные запросы при дальнейшей разработке, но SQL
injection не является главным риском текущего MVP.

Для сценария внутреннего контура с единственными внешними выходами в web search и
GigaChat API приоритетны следующие четыре проблемы.

1. **Отсутствие backend-аутентификации.** Сейчас знание адреса API достаточно для
   вызова backend независимо от frontend-login. Скомпрометированный компьютер во
   внутренней сети или украденная учётная запись могут обращаться к API напрямую.
   Нужно внедрить корпоративный SSO/OIDC/LDAP или серверные сессии/JWT, проверять
   пользователя на каждом маршруте, добавить RBAC и закрыть административные
   операции ролью владельца БЗ/администратора.
2. **Чрезмерно открытый API.** Без авторизации доступны не только `/query`, но и
   чтение диалогов и документов, feedback, переиндексация Wiki и изменение карты
   пробелов. Нужно разделить публичные для роли регистратора и административные
   маршруты, поставить reverse proxy/API gateway, ограничить сетевой доступ к API,
   добавить rate limiting, лимиты запросов и аудит действий.
3. **Доступ к чужим диалогам и пациентам.** `conversation_id` и идентификаторы
   ресурсов сейчас не связываются с authenticated user/role; внутренний клиент,
   знающий ID, потенциально может прочитать чужой контекст. Нужно ввести
   владельца/организационный scope для диалога, проверять право доступа к пациенту
   и conversation на backend, не доверять идентификаторам из frontend, минимизировать
   сохранение patient context и не хранить полную копию CRM без необходимости.
Внешний egress следует ограничить отдельным шлюзом: GigaChat API получает только
минимально необходимый обезличенный prompt, а web search — запросы и страницы из
разрешённых HTTPS-доменов. Необходимо заранее определить, допускается ли передача
любого patient context за пределы клиники; при запрете следует использовать
обезличивание или внутреннюю LLM. Шифрование PostgreSQL и backup остаётся нужным,
но является дополнительным слоем и не заменяет перечисленные проверки доступа.

### Рекомендуемая граница доверия

```text
Рабочее место регистратора
        │ SSO/session + RBAC
        ▼
API MedTrust ── mTLS/API gateway ── CRM/АРМ
   │  │  │
   │  │  └── allowlisted web gateway → внешние источники
   │  └──── PostgreSQL, закрытый network segment
   └─────── GigaChat/embeddings только через контролируемый egress
```

Для production необходимо отдельно решить, может ли какой-либо patient context
покидать внутренний контур. Если нет, в LLM/web-поиск следует передавать
обезличенный запрос и минимальные клинические признаки либо использовать
разрешённые внутренние модели/шлюзы. Даже при полном отсутствии внешнего трафика
остаются риски скомпрометированного рабочего места и злоупотребления правами.
