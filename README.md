# MedTrust — Path-Aware Hybrid RAG Backend

MVP backend для интеллектуального справочника регистратора. В проекте реализованы path-aware ingestion из Wiki.js Markdown, Qwen embeddings, PostgreSQL/pgvector + FTS, weighted RRF, GigaChat, долгосрочная память диалога и web-search fallback. Тематический scope guard на входе запроса отключён: запрос не блокируется по словарю ключевых слов.

## приоритет Wiki и проверка источников

В v26 локальная Wiki остаётся отправной точкой: поиск выполняется по каждой подтеме, а web-search включается только для подтем, для которых найденные Wiki-фрагменты недостаточны (кроме запросов о текущей погоде). Для web fallback используются явно указанные в Wiki города и ориентиры; координаты и точное совпадение адреса не требуются. Если Wiki задаёт город, внешние результаты, явно относящиеся к другому городу, отбрасываются.

Привязка утверждений к источникам выполняется приложением, а не по готовым меткам модели. Добавлено сопоставление характерных ориентиров и расширен словарь концепций в `app/services/source_relevance.py`. `answer_reviewed` означает, что проверка запущена и выполнена; `source_checks_passed` остаётся `true` только при подтверждении всех существенных утверждений и покрытия всех подтем. Эти флаги не являются гарантией медицинской истинности.

Подробности и ограничения: [`docs/RELEASE_NOTES_v26.md`](docs/RELEASE_NOTES_v26.md).

## Архитектура

```text
Frontend chat
     |
     v
POST /api/v1/query
     |
     +--> conversation_id -> PostgreSQL memory
     +--> contextualize follow-up
     +--> Qwen Embedding -> dense search
     +--> PostgreSQL FTS + path retrieval
     |               |
     |               v
     |           weighted RRF
     |               |
     |               v
     |       ranked Wiki candidates ---------+
     |          |                  |         |
     |     strong match       weak/no match  |
     |          |                  |         |
     |          |              SearXNG web  |
     |          |                  |         |
     +----------+------------------+---------+
                        |
                        v
               GigaChat answer generation
        (also runs when no sources were found)
                        |
                        v
    answer + source candidates + retrieval diagnostics
```

## Path-aware Wiki.js

В предоставленном `Суфлёр.zip` физическая папка не отражает всю логическую структуру. Источник структуры — поле `Путь:` внутри Markdown. Например:

```text
Путь: Регистратура/Словарь/Травматология/Общая_информация
```

Путь сохраняется как raw hierarchy и участвует в embedding text и path lexical signal. Поэтому `Регистратура/Словарь/Травматология` отличается от `Регистратура/Скрипты` не только URL, но и типом знания.

## Long-term memory и `conversation_id`

История хранится в PostgreSQL в таблицах `conversations`, `chat_messages`, `conversation_memory`.

Первый запрос:

```json
{
  "question": "Куда записать пациента при травме 5 дней назад?",
  "patient": null,
  "top_k": 5,
  "conversation_id": null
}
```

Backend создаёт `conversation_id` и возвращает его.

Frontend должен сохранить этот идентификатор и передавать его во все последующие запросы одного чата:

```json
{
  "question": "А если пациент уже обращался в другую клинику?",
  "conversation_id": "262298dd-fa67-4427-b4f1-8f10b4c03a0b"
}
```

По `conversation_id` backend загружает историю из PostgreSQL. Для follow-up вопросов формируется отдельный contextualized retrieval query, поэтому короткий вопрос не теряет объект предыдущего сообщения:

```text
Q1: Куда записать пациента при травме 5 дней назад?
Q2: А если пациент уже обращался в другую клинику?

Retrieval query:
Предыдущий вопрос: Куда записать пациента при травме 5 дней назад?
Уточняющий текущий вопрос: А если пациент уже обращался в другую клинику?
```

В GigaChat передаются summary и последние сообщения, а не неограниченная история.

## Web-search fallback

Web-search запускается только после проверки Wiki.js. Если лучший Wiki-кандидат недостаточно релевантен, backend обращается к локальному SearXNG, запущенному в Docker. API key для SearXNG не нужен.

Архитектура: `MedTrust → SearXNG → поисковые движки → WEB1..WEB3 → GigaChat`. SearXNG возвращает результаты через JSON API `/search?q=...&format=json`; в локальной конфигурации формат `json` включён в `searxng/settings.yml`.

Внешний поиск получает только contextualized question, без structured patient context. После поиска применяются правила:

1. сначала выполняется обычный поиск;
2. только HTTPS;
3. host должен совпасть с `WEB_SAFE_DOMAINS` или его поддоменом;
4. если безопасных результатов недостаточно, выполняется дополнительный поиск через `site:` по авторитетным доменам из `WEB_FALLBACK_DOMAINS`;
5. парсер собирает расширенный пул кандидатов (до 15, при необходимости до 30), а не прекращает поиск после первых трёх безопасных URL;
6. доменные fallback-запросы для известных медицинских тем используют англоязычные поисковые термины, чтобы повысить recall по NICE/PubMed при вопросах на русском языке;
7. заголовок и сниппет используются для отбрасывания явных противоречий, но отсутствие нужного термина в метаданных не считается достаточной причиной отказа: неоднозначные безопасные страницы ограниченно загружаются и проходят финальную проверку по полному тексту и типу запроса;
8. нерелевантные страницы исключаются до передачи источников в GigaChat; `RagService` повторно проверяет их перед генерацией и включением в `sources`;
9. после фильтрации выбираются максимум три результата: `WEB1`, `WEB2`, `WEB3`; при ошибке загрузки используется исходный поисковый сниппет, HTTP-редиректы при обогащении не следуются.

### Точный тест web-search

Для тестовой Wiki тема мигрени отсутствует. В `.env` должны быть:

```env
WEB_SEARCH_ENABLED=true
SEARXNG_URL=http://127.0.0.1:8080
WEB_SEARCH_TIMEOUT_SECONDS=15
WEB_SEARCH_FALLBACK_TIMEOUT_SECONDS=8
WEB_SEARCH_LANGUAGE=ru
WEB_FALLBACK_MAX_DOMAINS=4
WEB_FALLBACK_DOMAINS=nice.org.uk,pubmed.ncbi.nlm.nih.gov,cr.minzdrav.gov.ru,who.int
WEB_SOURCE_MAX_CHARS=6000
```

Запустить PostgreSQL и SearXNG:

```powershell
docker compose up -d db searxng
```

Проверить SearXNG в браузере:

```text
http://127.0.0.1:8080
```

Или проверить JSON API:

```powershell
Invoke-RestMethod "http://127.0.0.1:8080/search?q=мигрень&format=json"
```

В Swagger `http://127.0.0.1:8000/docs` выполнить `POST /api/v1/query`:

```json
{
  "question": "Какие современные рекомендации по диагностике мигрени у взрослых?",
  "patient": null,
  "top_k": 5,
  "conversation_id": null
}
```

Ожидаемое поведение при рабочем SearXNG: `web_search_attempted=true`; в `sources` должны быть погодные источники с `relevance.label="relevant"`. `used_in_answer=true` выставляется после детерминированного сопоставления содержимого ответа с текстом источника, а не только при наличии маркера, сгенерированного моделью. Без релевантного свежего прогноза сервис не подставляет выдуманную температуру.

При доступном SearXNG и наличии безопасных **и релевантных** результатов (в том числе найденных через доменный fallback) признаки успешного fallback:

```json
"web_search_attempted": true,
"web_search_used": true,
"web_search_status": "success"
```

Если поисковые движки возвращают безопасные, но не относящиеся к вопросу страницы, они отбрасываются и `web_search_status` отражает отсутствие релевантных результатов. Это не блокирует генерацию: модель всё равно отвечает из общих знаний, когда может, и явно отмечает, что подтверждения в найденных материалах нет. Если SearXNG недоступен или источники не найдены, сервис не выдумывает ссылки и не утверждает, что ответ подтверждён Wiki.

В `sources` возвращаются отобранные кандидаты; после генерации система удаляет недоверенные маркеры `[Wn]`/`[WEBn]` от модели и присваивает цитаты программно, если текст утверждения совпадает с текстом доказательства. `used_in_answer` означает, что как минимум одно утверждение было привязано к источнику; само по себе это не подтверждает полноту всего ответа.

Подробнее: `docs/WEB_SEARCH.md`.


## Поиск и генерация ответов

Входной тематический scope guard отключён: запрос не блокируется из-за отсутствия слова из фиксированного медицинского словаря. `/api/v1/query` расширяет пул кандидатов Wiki минимум до 12 фрагментов (с ограничением 30), а затем отдельно оценивает тематическую релевантность.

Для сочетания вопроса о парковке/допуске и вопроса о записи к врачу теперь используется фасетный поиск: запрос разбивается на отдельные подзапросы, каждый ищется независимо, а совпадающие чанки объединяются. В ответе API поле `retrieval_queries` показывает фактически использованные подзапросы; `sources[].matched_query_aspects` и `retrieval[].matched_query_aspects` показывают, для какой части запроса найден документ. Число `resource_usage.embedding_api_calls` учитывает отдельные embeddings-запросы.

Классификатор различает общие правила парковки пациентов и условия только для такси, а для вопроса о консультации ревматолога приоритизирует Wiki-раздел «Распределение записи» с именами врачей. Например, на вопрос о парковке на Садовой 15 и консультации ревматолога контекст должен содержать оба источника: правила парковки для пациентов (3 часа бесплатно, затем 300 рублей за полный или неполный час) и имена врачей из раздела о распределении записи.

### Формат ответа

Системный промпт GigaChat просит по умолчанию давать короткие маркированные пункты: обычно 3–7, одна основная мысль на пункт; для последовательности действий — нумерованный список. Простой запрос не должен раздуваться до 7 пунктов. Это проверяет форматирование, но гипотезу об уменьшении времени восприятия нужно подтвердить пользовательским A/B-тестом с регистраторами: текущие unit-тесты не измеряют скорость чтения.

### Релевантность источников и несколько документов

`app/services/source_relevance.py` содержит детерминированный классификатор `relevant / partial / irrelevant` со score, причиной и совпавшими терминами. Для Wiki учитываются заголовок, путь, раздел, URL и содержимое; отдельно оценивается body-level соответствие конкретного чанка. В контекст сначала выбираются лучшие фрагменты из разных документов, после чего могут добавляться полезные дополнительные чанки. Один высокий `dense_similarity` не может вытеснить точное совпадение по пути или содержимое другой статьи. Нерелевантные Wiki-кандидаты остаются в `retrieval` для диагностики, но не засоряют prompt, если классификатор нашёл релевантные материалы.

Веб-результаты проходят HTTPS + allowlist, тематическую проверку домена/типа запрашиваемой информации и проверку содержательности текста. Для погодных запросов выделены погодные провайдеры; «Погода Екатеринбург» всегда запускает SearXNG, даже если Wiki вернула высокий similarity. Проверяется совпадение города, включая популярные варианты русской/английской транслитерации. Если актуальный прогноз из источников не получен, сервис не выдумывает погодные значения и сообщает об ошибке получения текущих данных.

В `sources[].relevance` возвращается оценка каждого источника; для Wiki в `retrieval[].source_relevance` и `retrieval[].content_relevance` видны оценка статьи и оценка тела чанка. В `retrieval[].eligible_for_answer` отмечено, попал ли фрагмент в контекст генерации. `sources[].used_in_answer` означает, что система смогла связать с источником хотя бы одно утверждение по текстовому доказательству. `answer_review_diagnostics.claim_attribution` показывает результат на уровне утверждения, а `facet_coverage` — покрытие каждой подтемы вопроса. Это детерминированные эвристики, не гарантия фактической или клинической безошибочности.

Постгенерационная жёсткая валидация по-прежнему не блокирует ответ из-за отсутствующей цитаты или фиксированного чек-листа. После генерации система сама сопоставляет утверждения с фрагментами источников; маркеры от GigaChat не считаются доказательством. `answer_reviewed` означает, что детерминированная проверка была выполнена, `source_checks_passed` — что утверждения и все запрошенные подтемы получили подтверждение. Для составного вопроса каждая подтема ищется отдельно; если Wiki её не покрывает, запускается web-search именно по этой подтеме. Если web тоже не вернул подтверждение, `facet_coverage[].covered=false` и `source_checks_passed=false`, даже когда остальные части ответа обоснованы. Для live-weather без релевантных погодных данных текущий прогноз не генерируется.

## История изменений

В v20 исправлялось дублирование разделов в компактном NICE-шаблоне. В v21 отключили блокирующий медицинский чек-лист. В v22 дополнительно отключён тематический scope guard, порог similarity перестал исключать Wiki-фрагменты из контекста, а отсутствие источников или цитат больше не блокирует генерацию ответа. В v23 добавлены классификатор релевантности источников и ранжирование чанков по конкретной теме. В v24 составные запросы по парковке и записи к специалисту ищутся отдельными фасетами; отбор различает общие условия парковки пациентов и специальные правила для такси, а раздел с распределением приёма специалистов распознаётся как прямой ответ на вопрос о записи.

### Полный текст клинических рекомендаций NICE

Когда SearXNG возвращает обзор NICE вместо содержательного раздела, MedTrust автоматически получает страницу `/guidance/<id>/chapter/recommendations` для запросов о диагностике, лечении, симптомах или рекомендациях. Парсер отдаёт RAG основной текст страницы, а не только обзорный сниппет; ссылки в `sources` ведут на фактически использованный раздел. Для вопроса о диагностике мигрени у взрослых при наличии полного набора разделов используется краткий шаблон без вызова GigaChat; если доступен лишь короткий фрагмент таблицы, ответ ограничивается подтверждёнными признаками боли и явно предупреждает, что полного текста недостаточно.


### Диагностика и контроль расходов (v25)

`POST /api/v1/query` возвращает `answer_review_diagnostics`, `answer_validation_mode`, `answer_reviewed`, `source_checks_passed` и `resource_usage`. Режим `deterministic_source_attribution_and_facet_coverage` выполняет локальную проверку источников и полноты подтем без повторных вызовов GigaChat. `answer_reviewed=true` говорит, что проверка выполнена; `source_checks_passed=true` устанавливается только когда все значимые утверждения и все подтемы сопоставлены с доказательствами. При частичном результате ответ не удаляется, но диагностика остаётся `partial`/`insufficient_evidence`.

Обычный запрос без детерминированного FAQ-шаблона выполняет максимум один вызов GigaChat, включая случаи, когда Wiki и web не вернули пригодных источников. Шаблон на основе полного текста NICE может вернуть ответ с `gigachat_calls=0`. `resource_usage` показывает фактические вызовы и токены, когда провайдер возвращает usage metadata; параметры `GIGACHAT_MAX_TOKENS`, `RAG_MAX_WEB_SOURCES`, `RAG_MAX_WIKI_SOURCES`, `RAG_MAX_SOURCE_CHARS`, `RAG_MAX_HISTORY_MESSAGES` и `MEMORY_SUMMARY_ENABLED` продолжают ограничивать расходы.

Целевые precision, recall и accuracy выше 0.95 пока не подтверждены: их нужно измерить на размеченном наборе запросов с независимой оценкой источников и фактических утверждений.
